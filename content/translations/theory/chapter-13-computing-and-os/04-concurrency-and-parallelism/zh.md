# 并发与并行

*并发与并行让程序能够管理或执行多个任务。本篇介绍两者的区别、同步原语、经典并发问题、死锁、无锁数据结构、并行编程模型、异步编程和扩展定律。这些概念用于多线程服务器、分布式训练和现代应用。*

- 单核处理器可以在多个任务之间切换；多核 CPU 和 GPU 则有多个硬件执行单元，能够同时处理不同任务。即使只有一个核心，系统也可能在下载文件、渲染界面和处理用户输入之间切换。**并发**和**并行**是处理多项活动的两种方式。处理器还可能利用流水线或超标量执行，在一个周期内执行多条指令。

## 并发与并行

![并发是在单个核心上交错执行任务；并行是在多个核心上同时执行任务](../images/concurrency_vs_parallelism.svg)

- **并发**关注如何管理多个任务。任务可以交错推进：任务 A 运行一段时间，再运行任务 B，然后回到任务 A。在单核上，任务轮流使用处理器，看起来像同时进行，但同一时刻并没有多个任务在不同核心上执行。

- **并行**指多个任务在同一时刻执行。若有 $n$ 个硬件执行单元，最多可以同时运行 $n$ 个任务。

- 可以把并发想成一位厨师在切菜和搅拌之间来回切换；并行则像两位厨师同时各做一件事。系统可以只有并发而没有并行（单核交错处理任务），也可以让多个互不交互的程序并行运行；实际系统通常两者兼有。

- 在机器学习中，数据加载可以与 GPU 计算重叠，这是并发；分布式训练中的多 GPU 同时计算梯度，则是并行（第 6 章）。

## 同步原语

- 多个线程共享数据时，需要**同步**来避免竞态条件。若程序结果取决于不可预测的线程执行顺序，就可能发生**竞态条件**。

- 假设两个线程都要将共享计数器加 1。表达式 counter += 1 通常包含读取计数器、加 1、写回三个步骤。如果两个线程都读到 5，各自加 1 后都写入 6，最终计数器就是 6，而不是预期的 7；其中一次更新丢失了。

- **互斥锁**（mutex）保证同一时刻只有一个线程进入临界区。线程进入前**获取**锁，离开后**释放**锁。若其他线程尝试获取已被占用的锁，就必须等待。

```
lock.acquire()
counter += 1      # only one thread at a time here
lock.release()
```

- 互斥锁可以保护共享状态，但会引入**锁竞争**：多个线程争用同一把锁时，等待时间会增加，程序的可扩展性也会下降。若所有线程都必须依次通过同一把锁，程序的这一部分就会串行执行。

- **信号量**比互斥锁更通用。计数信号量维护可用资源数量：wait() 在资源可用时取走一个名额，否则等待；signal() 归还一个名额。初值为 1 的信号量可实现互斥；初值为 $n$ 时，最多允许 $n$ 个线程同时使用资源，适合数据库连接池等场景。

- **条件变量**让线程等待某个条件成立。线程在持有关联锁时检查条件；若条件不成立，就原子地释放锁并等待通知。收到通知后，线程重新获取锁并再次检查条件。通常要在循环中检查，以应对虚假唤醒和其他线程先一步改变状态的情况。这样可以避免忙等。

- **监视器**将互斥锁、条件变量和共享数据封装成一个同步抽象。Java 的 synchronized 关键字和 Python 的 threading.Condition 可提供监视器式的同步能力。

- **读写锁**区分读者和写者：多个读者可以同时读取，写者则需要独占访问。读写锁适合读操作远多于写操作的场景，例如缓存模型预测结果；实际收益取决于锁实现、线程数量和读写比例，也要考虑写者可能等待过久。

## 经典并发问题

- **生产者—消费者问题**（有界缓冲区）：生产者生成项目并放入固定大小的缓冲区，消费者从中取出项目。缓冲区满时生产者要等待，缓冲区空时消费者要等待；两者还必须避免并发修改导致的数据损坏。

- 一种常见方案用两个信号量分别记录空槽和已占用槽，再用互斥锁保护缓冲区。这种模式常见于消息队列、日志系统和数据处理管线。

- **读者—写者问题**：多个读者可以同时读取，但写者需要独占访问。若读者不断到来，写者可能饥饿。不同方案可以优先读者、优先写者，或在两者之间提供公平调度。

- **哲学家就餐问题**：五位哲学家围桌而坐，相邻哲学家之间各有一把叉子。每人需要同时拿到两把叉子才能吃饭。若五人同时拿起左边的叉子，每人都会等待右边的叉子，形成死锁。可采用多种方案，例如原子地取得两把叉子、让一位哲学家改变拿叉顺序，或用信号量限制同时就餐人数最多为 4。

## 死锁

- **死锁**是指一组线程互相等待对方持有的资源，依赖关系形成环路，导致没有线程能够继续执行。

![死锁示意：线程 A 持有锁 1 并等待锁 2；线程 B 持有锁 2 并等待锁 1，形成循环等待](../images/deadlock_cycle.svg)

- 死锁可能发生时，以下四个**必要条件**必须同时满足：

    1. **互斥**：某项资源同一时刻只能由一个线程持有。
    2. **占有并等待**：线程持有至少一项资源，同时等待另一项资源。
    3. **不可抢占**：资源不能被强行从持有线程手中夺走。
    4. **循环等待**：等待关系中存在一个环。

- **死锁预防**通过打破至少一个必要条件来避免死锁：
    - 打破循环等待：为资源规定全序，所有线程按相同顺序获取资源。例如，所有线程都先获取锁 A 再获取锁 B，就不会因获取顺序相反而形成等待环。
    - 打破占有并等待：要求线程一次性申请所需资源，再开始执行；这样可能降低资源利用率。

- **死锁避免**会动态判断是否应授予资源请求。**银行家算法**记录每个线程声明的最大资源需求，只在授予请求后仍存在让所有线程最终完成的安全顺序时才批准。其复杂度随线程数和资源种类增加，常见分析为 $O(n^2m)$（$n$ 个线程，$m$ 种资源），实际系统很少在每次请求时运行该算法。

- **死锁检测**允许死锁发生，再寻找并恢复。对每类资源只有一个实例的情况，可以在等待图中查找环；若有多实例资源，则需要更一般的检测算法。恢复方法包括终止线程或回滚事务。

- 实际系统常通过锁排序等方法预防常见死锁，也会在数据库事务等场景中检测死锁并中止其中一个事务，以打破等待环。

## 无锁和无等待数据结构

- 锁可能造成竞争、优先级反转和死锁。**无锁算法**不用互斥锁，而是通过硬件提供的**原子操作**协调并发访问。

- 一种常见的原子操作是**比较并交换**（CAS）：检查内存位置当前值是否等于预期值；若相等，就原子地写入新值并报告成功，否则报告失败。不同硬件可能以单条指令或等价机制实现 CAS。伪代码如下：

```
CAS(address, expected, new_value):
    if *address == expected:
        *address = new_value
        return true
    else:
        return false
```

- 无锁算法常在循环中使用 CAS：读取当前值，计算新值，再尝试更新。如果另一线程已经修改该值，CAS 就会失败，当前线程需要重试。个别线程可能长期重试。

- **无锁进展保证**：无论其他线程如何延迟，系统整体都能在有限步内由某个线程取得进展；它不保证每个线程都能完成。

- **无等待进展保证**：每个线程都能在有界步数内完成操作，是比无锁更强的保证，也更难实现。

- 无锁栈、队列和哈希表可用于高性能系统。Java 的 ConcurrentHashMap 和 Go 的原子操作会使用 CAS 等机制，但这不意味着它们的所有操作都是无锁实现。

## 并行编程模型

- **共享内存并行**：多个线程访问同一内存空间，因此程序员需要负责同步。**OpenMP**可通过编译器指令并行化循环：

```c
#pragma omp parallel for
for (int i = 0; i < n; i++) {
    result[i] = compute(data[i]);
}
```

- 编译器会将循环迭代分配给可用 CPU 核心。OpenMP 适合对多个数据点执行相同操作的数据并行任务，常用于科学计算。

- **消息传递并行**：每个进程拥有独立内存，进程之间通过发送和接收消息通信。**MPI**（消息传递接口）是跨节点分布式计算的常用标准：

```c
MPI_Send(data, count, MPI_FLOAT, dest, tag, MPI_COMM_WORLD);
MPI_Recv(data, count, MPI_FLOAT, src, tag, MPI_COMM_WORLD, &status);
```

- 由于各进程没有共享状态，MPI 可扩展到大量节点，但程序仍需处理通信和同步。分布式深度学习会使用 MPI_AllReduce 等集合通信来同步多个 GPU 的梯度；环形 AllReduce 是一种常见实现方式，具体算法取决于库和硬件。

- **GPU 并行**通常采用 **SIMT**（单指令、多线程）执行模型：大量线程对不同数据执行同一类指令。这适合矩阵运算，因为相同的乘加操作可应用于许多元素。GPU 编程会在后续章节详细介绍。

## 异步和事件驱动编程

- 并发不一定需要多个线程。对于大量 I/O 等待任务，**异步编程**可通过单线程**事件循环**管理许多任务，前提是 I/O 操作不会阻塞事件循环。

- 事件循环维护任务队列。任务需要等待网络响应或文件读取时，会注册回调或等待对象并让出控制权。事件循环随后执行其他已就绪任务；I/O 完成后，再安排原任务继续执行。等待 I/O 时，不必让一个线程一直阻塞在该任务上。

- **协程**是可以暂停并在之后恢复执行的函数。Python、JavaScript 和 Rust 等语言提供 async/await 语法，让协程看起来接近顺序代码：

```python
async def fetch_data(url):
    response = await http_get(url)  # suspends here, event loop runs other tasks
    return process(response)         # resumes when response arrives
```

- await 会暂停当前协程并将控制权交还事件循环。等待的操作完成后，协程从暂停处继续执行。这属于合作式多任务：协程主动让出控制权；抢占式多任务则由操作系统强制切换线程。

- 异步适合有大量并发连接的 **I/O 密集型**任务，例如同时服务数千个客户端。它本身不会让单线程事件循环利用多个核心，因此不适合直接加速 **CPU 密集型**任务；这类任务可使用多线程或多进程。

- 标准版 CPython 的**全局解释器锁**（GIL）限制多个线程同时执行 Python 字节码，因此 CPU 密集型 Python 代码通常用多进程实现并行；异步则常用于 I/O 并发。Python 3.13 引入了可选的无 GIL 构建，但默认构建仍使用 GIL；原生扩展也可能在执行期间释放 GIL。

## 扩展定律

- **阿姆达尔定律**描述并行化可能带来的理论加速比。设程序中比例为 $p$ 的部分可并行，其余 $1-p$ 必须串行：

$$\text{Speedup}(n) = \frac{1}{(1-p) + \frac{p}{n}}$$

![阿姆达尔定律：串行部分限制最大加速比；若 10% 的工作必须串行，最大加速比为 10 倍](../images/amdahl_serial_bottleneck.svg)

- 其中 $n$ 是处理器数量。当 $n\to\infty$ 时，最大加速比趋近 $\frac{1}{1-p}$。若程序 95% 的工作可并行，则无论增加多少核心，理论加速比最多为 $\frac{1}{0.05}=20\times$；串行部分会成为瓶颈。

- 这对机器学习很重要：若 10% 的训练时间用于无法与计算重叠的数据加载，那么单靠增加 GPU，理论加速比最多为 10 倍。改进数据管线、让 I/O 与计算重叠，可以减少这一串行部分（第 6 章）。

- **古斯塔夫森定律**提供了另一种视角。它不固定问题规模再增加处理器，而是固定运行时间，考察增加处理器后可以完成多少工作。若并行部分随问题规模增长：

$$\text{Speedup}(n) = 1 - p + p \cdot n$$

- 该加速比随 $n$ 线性增长。其出发点是：处理器更多时，可以在相同时间内处理更大的问题，而不只是更快地解决原问题。在机器学习中，使用更多 GPU 并扩大批次规模属于**弱扩展**；固定批次规模、观察加速比则属于**强扩展**。

## 编程任务（使用 Colab 或笔记本）

1. 演示竞态条件。两个线程不加同步地递增共享计数器，并观察是否出现更新丢失。

```python
import threading

counter = 0

def increment(n):
    global counter
    for _ in range(n):
        counter += 1  # NOT atomic: read, add, write

threads = [threading.Thread(target=increment, args=(100000,)) for _ in range(4)]
for t in threads: t.start()
for t in threads: t.join()

print(f"Expected: {4 * 100000}")
print(f"Actual:   {counter}")
print(f"Lost updates: {4 * 100000 - counter}")
```

在标准 CPython 中，GIL 会影响线程交错，因此这段代码不保证每次运行都出现丢失更新；未观察到错误也不能证明代码线程安全。竞态条件的结果取决于运行时、线程调度和执行环境。

2. 使用锁修复竞态条件，并测量同步开销。

```python
import threading
import time

lock = threading.Lock()
counter = 0

def increment_locked(n):
    global counter
    for _ in range(n):
        with lock:
            counter += 1

start = time.time()
threads = [threading.Thread(target=increment_locked, args=(100000,)) for _ in range(4)]
for t in threads: t.start()
for t in threads: t.join()
elapsed = time.time() - start

print(f"Counter: {counter} (correct: {4 * 100000})")
print(f"Time with lock: {elapsed:.3f}s")
```

这段代码重新初始化计数器并在每次更新时获取锁。运行时间还受系统负载、线程调度和计时精度影响，因此结果只能作为示例测量，不能直接视为锁本身的固定成本。

3. 可视化阿姆达尔定律，绘制不同并行比例下，加速比随处理器数量的变化图。

```python
import jax.numpy as jnp
import matplotlib.pyplot as plt

n_procs = jnp.arange(1, 65)

for p, color in [(0.5, "#e74c3c"), (0.9, "#f39c12"), (0.95, "#27ae60"), (0.99, "#3498db")]:
    speedup = 1 / ((1 - p) + p / n_procs)
    plt.plot(n_procs, speedup, color=color, linewidth=2, label=f"p={p}")
    # Max speedup line
    plt.axhline(1 / (1 - p), color=color, linestyle="--", alpha=0.3)

plt.xlabel("Number of processors")
plt.ylabel("Speedup")
plt.title("Amdahl's Law: Serial Fraction Limits Speedup")
plt.legend()
plt.grid(True)
plt.show()
```
