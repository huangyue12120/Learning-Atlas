# 操作系统

*操作系统是位于硬件与应用之间的软件层，负责管理资源、提供抽象并实施隔离。本篇涵盖操作系统的职责、进程、线程、CPU 调度、内存管理、文件系统和系统调用。*

- 没有操作系统的计算机，就像没有厨师的厨房：食材（硬件）都在，但没有人协调谁使用炉灶、盘子放在哪里，也没有人防止两个人同时抢同一把刀。**OS** 就是这个协调者。

- 对机器学习实践者而言，操作系统概念可以解释：为什么 `nvidia-smi` 会显示每个进程的 GPU 显存使用量，为什么训练会因“out of memory”崩溃，为什么 `fork()` 会复制你的 Python 进程，以及为什么 Docker 容器能提供隔离环境。

## 操作系统做什么

- 操作系统有三个核心职责：

    - **抽象**：用清晰的接口隐藏硬件复杂性。程序读写“文件”时不必知道底层存储是 SSD、HDD 还是网络盘；分配“内存”时不必管理物理 RAM 芯片；运行在“CPU”上时不必操心中断和缓存一致性。

    - **资源管理**：多个程序共享 CPU、内存、磁盘和网络。操作系统决定谁在什么时候得到什么资源，以及能用多长时间。公平且高效的分配策略能让系统保持响应。

    - **隔离与保护**：程序不能互相干扰。浏览器中的 bug 不应让内核崩溃，恶意程序不应读取另一个程序的密码。操作系统借助硬件支持（权限级别、虚拟内存）实施边界。

## 进程

- **进程**是正在运行的程序，是操作系统最基本的工作单位。每个进程包含：

    - **代码**（程序指令，只读）。
    - **数据**（全局变量、堆分配）。
    - **栈**（函数调用帧、局部变量）。
    - **状态**（寄存器值、程序计数器、打开的文件等）。

- **进程控制块（PCB）**是操作系统用来追踪进程的数据结构。它保存进程 ID（PID）、状态、程序计数器、寄存器内容、内存映射、打开的文件描述符和调度优先级。当操作系统从一个进程切换到另一个进程时，会把当前进程的状态保存到 PCB，再加载下一个进程的状态，这就是**上下文切换**。

- 上下文切换代价很高：保存和恢复寄存器、刷新缓存、使 TLB 条目失效都需要微秒级时间。在同时运行数千个进程的系统中，这种开销可能很大。因此，按请求创建一个进程的服务器架构（例如早期 Apache）被基于线程或事件驱动的架构取代。

- Unix 中通过 `fork()` 和 `exec()` 创建进程：

    - `fork()` 创建当前进程的**副本**。子进程会得到父进程内存、文件描述符和状态的副本。两个进程从同一点继续执行，但 `fork()` 在子进程中返回 0，在父进程中返回子进程的 PID。

    - `exec()` 用新程序替换当前进程的代码。`fork()` 之后，子进程通常调用 `exec()` 来运行另一个程序。

    - 这种先 fork 后 exec 的模式很优雅：创建新进程（fork）与加载新程序（exec）是两个可以独立定制的操作。在 fork 和 exec 之间，子进程可以重定向 I/O、修改环境变量或降低权限。

![进程状态转换：新建 → 就绪 → 运行 → 阻塞/终止，并包含抢占和 I/O 等待](../images/process_states.svg)

- **进程状态**：进程会处于以下某一种状态：
    - **运行**：当前正在某个 CPU 核心上执行。
    - **就绪**：等待 CPU 核心（可以运行但尚未被调度）。
    - **阻塞**（等待中）：必须等某个事件发生才能继续（I/O 完成、获得锁或计时器到期）。
    - **终止**：执行完成，等待父进程收集退出状态。

## 线程

- **线程**是进程内部的轻量级执行单位。同一进程中的所有线程共享代码、数据和堆，但每个线程都有自己的栈和寄存器状态。

- 与多个进程相比，线程的优势在于共享内存，因此线程间通信很快（只需读写共享变量）。进程则需要进程间通信（管道、套接字、共享内存映射），速度更慢也更复杂。

- 缺点是共享内存很危险。两个线程同时写同一个变量会造成**竞态条件**（结果取决于哪个线程先运行）。这会引出同步问题，将在第 04 篇讨论。

- **内核线程**由操作系统调度器管理，每个线程都能独立调度到 CPU 核心上。创建和切换内核线程需要系统调用，开销与进程上下文切换相近（但稍低）。

- **用户线程**（绿色线程）由用户空间的运行时库管理，操作系统看不见它们。创建和切换它们更便宜（不需要系统调用），但一个用户线程的阻塞操作会阻塞进程中的所有线程（因为操作系统只看到一个内核线程）。

- 现代系统使用**混合模型**：把许多用户线程映射到较少的内核线程上（M:N 线程）。Go 的 goroutine 和 Erlang 的 process 都是由语言运行时调度到操作系统线程上的用户级线程。

- **线程池**预先创建固定数量的线程，让它们等待任务。任务到达时分配给空闲线程。这样可以避免为每个任务创建和销毁线程的开销。Web 服务器、数据库引擎和 ML 推理服务器都使用线程池。

## CPU 调度

- **调度器**决定每个时刻哪个进程/线程运行在哪个 CPU 核心上。目标包括：最大化 CPU 利用率、最小化交互任务的响应时间、最大化批处理任务的吞吐量，并保证公平。

- **先到先服务（FCFS）**：进程按到达顺序运行。它简单，但会出现**护航效应**：一个长时间运行的进程阻塞后面所有短进程。

- **最短作业优先（SJF）**：先运行最短的进程。它能被证明可以最小化平均等待时间，但要求事先知道作业长度（通常不可能）。抢占式版本叫**最短剩余时间优先（SRTF）**：短作业到达时会中断当前作业。

- **轮询（RR）**：每个进程获得固定的**时间片**（例如 10 ms），时间片用完后被抢占并移到队列末尾。它公平且响应快，但时间片很关键：太小会导致过多上下文切换，太大会退化成 FCFS。

- **优先级调度**：每个进程都有优先级，高优先级进程先运行。危险在于**饥饿**：如果高优先级进程不断到达，低优先级进程可能永远无法运行。**老化**可以解决这个问题：进程等待越久，优先级越高。

- **多级反馈队列（MLFQ）**：使用多个优先级和时间片不同的队列。新进程从最高优先级队列开始（时间片短）；如果进程用完整个时间片（说明受 CPU 限制），就降到更低优先级的队列（时间片更长）。交互进程在用完时间片前就因 I/O 阻塞，因此会自然地留在高优先级队列。它无需预先知道作业类型，就能适应工作负载。

- **完全公平调度器（CFS）**是 Linux 调度器。它维护一棵按“虚拟运行时间”排序的红黑树（平衡二叉搜索树），虚拟运行时间表示进程已经消耗的 CPU 时间。虚拟运行时间最小的进程下一个运行。这样随着时间推移，每个进程都能得到公平份额。CFS 每次调度决策的复杂度为 $O(\log n)$。

## 内存管理

- 操作系统管理物理 RAM，把它分配给进程，并在不再需要时回收。

- **分页**（第 02 篇）把虚拟内存划分为固定大小的页，把物理内存划分为页框。页表把页映射到页框。由于所有页大小相同，分页消除了外部碎片（分配之间的浪费空间）。

- **按需分页**只在页面第一次被访问时把它加载到 RAM，而不是进程启动时就加载。这可以节省内存：一个拥有 1 GB 代码的程序，在典型运行中可能只使用 50 MB，其余部分根本不会被加载。

- RAM 已满而又需要新页面时，操作系统必须**淘汰**一个已有页面。**页面置换**算法（第 02 篇的 LRU、FIFO、clock）决定淘汰哪个页面。好的置换策略会减少缺页，坏的策略会导致抖动。

- **分段**把内存划分为可变大小的段（代码、数据、栈、堆），每个段有自己的基地址和长度。分段提供逻辑组织，分页负责物理管理。现代系统很少使用分段（主要用于保护），而依赖分页进行内存管理。

- **堆**是动态分配内存所在的位置（C 中的 `malloc`/`free`、Java 中的 `new`、Python 中隐式使用）。操作系统向进程提供大块内存，**内存分配器**（例如 `glibc malloc`、`jemalloc`、`tcmalloc`）再把大块细分为较小的分配。分配器设计会影响性能：碎片浪费空间，线程之间的竞争浪费时间。

## 文件系统

- **文件系统**把持久化存储上的数据组织成由文件名和目录名构成的层级结构。

- **inode（索引节点）**保存文件元数据：大小、所有者、权限、时间戳和磁盘数据块指针。文件名存放在目录中，目录把名称映射到 inode 编号。这种分离意味着一个文件可以有多个指向同一 inode 的名称，即**硬链接**。

- **FAT（File Allocation Table，文件分配表）**是 USB 驱动器和 SD 卡常用的简单文件系统。它把每个簇（块）映射到文件中的下一个簇，形成链表。它简单，但对权限、日志和大文件的支持不好。

- **ext4** 是默认的 Linux 文件系统。它使用直接、间接、二级间接和三级间接块指针处理任意大小的文件；还支持**extent（连续块范围）**，提高大文件效率。最大文件大小为 16 TB，最大分区大小为 1 EB。

- **日志**可以防止崩溃导致的损坏。修改文件系统结构前，先把变更写入**日志（journal）**。如果系统在操作中途崩溃，重启时会重放日志，以完成或撤销操作。没有日志时，写入过程中崩溃可能让文件系统处于不一致状态（例如文件数据块已经更新，但 inode 没有更新，或反过来）。

- **基于 B-tree 的文件系统**（Btrfs、ZFS）使用 B-tree（平衡搜索树）组织数据和元数据，支持高效搜索、写时复制快照以及内置的数据完整性校验和。这些 B-tree 与数据库索引使用的是同一种结构。

## 系统调用与内核模式

- **系统调用**是用户程序与操作系统内核之间的接口。当程序需要执行特权操作（读文件、分配内存、创建进程、发送网络包）时，就会发起系统调用。

- CPU 在两种模式下运行：
    - **用户模式**：受限。程序可以执行自己的代码、访问自己的内存，但不能直接访问硬件、其他进程的内存或操作系统数据结构。
    - **内核模式**：不受限。操作系统内核可以访问所有硬件和内存。系统调用是从用户模式进入内核模式的受控入口。

- 程序调用 `read()` 时，会发生以下事情：
    1. 程序把参数放入寄存器并触发 **trap（陷阱）**（一种软件中断）。
    2. CPU 切换到内核模式，跳转到系统调用处理器。
    3. 内核验证参数，执行 I/O 操作，并把数据复制到用户缓冲区。
    4. 内核切回用户模式并返回结果。

- 常见系统调用包括：`open`、`read`、`write`、`close`（文件），`fork`、`exec`、`wait`、`exit`（进程），`mmap`、`brk`（内存），`socket`、`bind`、`listen`、`accept`（网络）。

- **中断**是迫使 CPU 暂停当前工作、转而运行内核中断处理程序的硬件信号。键盘按键、网络包到达和计时器 tick 都会产生中断。计时器中断尤其重要：它让操作系统能够抢占正在运行的进程并切换到另一个进程，从而实现抢占式多任务。

## 网络基础

- 网络栈是操作系统中支持机器间通信的子系统。理解它可以解释分布式训练如何同步梯度、模型服务如何处理请求，以及延迟为什么重要。

![TCP/IP 协议栈：应用层、传输层、网络层和链路层逐层添加头部](../images/tcp_ip_layers.svg)

- **TCP/IP 模型**把网络组织成多层，每层为上一层提供抽象：

    - **链路层**：处理单条物理链路上的通信（以太网、Wi-Fi），负责 MAC 地址和帧。
    - **网络层（IP）**：把数据包从源地址跨多个网络路由到目的地址。每台机器都有一个 **IP 地址**（例如 IPv4 的 192.168.1.1，或 128 位的 IPv6 地址）。路由器根据目的 IP 逐跳转发数据包。
    - **传输层（TCP/UDP）**：提供应用之间的端到端通信。
    - **应用层**：HTTP、DNS、gRPC 等应用直接使用的协议。

- **TCP（Transmission Control Protocol，传输控制协议）**提供可靠、有序的传输。它会建立连接（三次握手：SYN、SYN-ACK、ACK），用序列号和确认保证数据按序到达，重传丢失的数据包，并控制发送速率以免压垮网络（**拥塞控制**）。代价是延迟：握手增加一次往返，重传也会增加等待。

- **UDP（User Datagram Protocol，用户数据报协议）**提供不可靠、无序的传输。不需要握手，也不重传，不保证顺序。它的延迟远低于 TCP，适用于速度比可靠性更重要的场景：视频流、在线游戏和 DNS 查询。在机器学习中，一些梯度同步协议使用基于 UDP 的 RDMA 来降低延迟。

- **套接字**是操作系统提供的网络通信 API。**socket** 是由（IP 地址、端口号）标识的端点。服务器创建 socket，把它绑定到端口（例如 HTTP 的 80），监听连接并接受连接；客户端创建 socket，连接到服务器的地址和端口。之后，数据就像文件一样通过 socket 读写。

- **DNS（Domain Name System，域名系统）**把人类可读的名称（google.com）转换为 IP 地址（142.250.80.46）。它是分布式、分层的数据库：机器询问本地解析器，本地解析器询问根服务器，根服务器再把请求委托给各域名的权威服务器。

- **HTTP（HyperText Transfer Protocol，超文本传输协议）**是 Web 的请求—响应协议。客户端发送请求（方法 + URL + 请求头 + 可选正文），服务器返回响应（状态码 + 请求头 + 正文）。机器学习模型服务（例如 TensorFlow Serving、Triton）通过 HTTP 或 gRPC 端点提供模型。

- **延迟与带宽**：延迟是一个数据包从源到目的地所需的时间（由物理距离和网络跳数决定）；带宽是数据速率（每秒能传输多少字节）。高带宽、高延迟的连接（卫星互联网）可以传输大量数据，但每个字节都需要很久才能到达。对分布式训练而言，**延迟**影响同步屏障（所有 GPU 都要等待最慢的那个），而**带宽**影响大型梯度张量的传输（第 6 章）。

## 虚拟化与容器

- **虚拟化**让多套操作系统运行在一台物理机器上。**虚拟机监控器**（VMware、KVM、Xen）创建**虚拟机（VM）**，每台 VM 都有自己的虚拟 CPU、内存、磁盘和网络接口。每台 VM 运行一套完整的操作系统（客户机 OS），并以为自己拥有专用硬件的方式工作。

- VM 提供强隔离（一个 VM 崩溃不会影响其他 VM）和灵活性（同一台机器上运行 Linux 和 Windows，也可以在物理主机之间迁移 VM）。代价是开销：每台 VM 都运行完整的 OS 内核，为与宿主机重复的 OS 操作消耗内存和 CPU。

![虚拟机在虚拟硬件上运行独立的客户机 OS；容器共享宿主机内核，轻量得多](../images/container_vs_vm.svg)

- **容器**（Docker、Podman）提供了更轻量的替代方案。它们不虚拟化整套硬件，而是共享宿主机 OS 内核，并使用内核功能隔离进程：

    - **命名空间**隔离进程能看到的内容：每个容器都有自己的进程树视图（PID namespace）、网络接口（network namespace）、文件系统挂载点（mount namespace）和主机名（UTS namespace）。容器内的进程看不到其他容器中的进程。

    - **Cgroups（控制组）**限制进程可以使用的资源：CPU 时间、内存、磁盘 I/O 和网络带宽。容器不能使用超过其 cgroup 允许的资源，从而防止一个容器耗尽其他容器的资源。

- 容器在毫秒级启动（无需启动操作系统），开销很小（共享内核），并由 **Dockerfile** 定义基础镜像、依赖和命令。这使环境具有可复现性：`docker build` 在不同机器上都能生成相同环境。

- 对机器学习而言，容器解决了“在我的机器上能运行”的问题。包含特定 CUDA、cuDNN、PyTorch 和 Python 版本的训练环境可以打包成容器镜像，任何人都能在任意机器上复现精确环境。云训练平台（AWS SageMaker、GCP Vertex AI）也在容器中运行训练作业。

- **Kubernetes（K8s）**在规模上编排容器：把容器调度到集群中的机器，重启失败容器，根据负载扩缩容，并管理容器之间的网络。大规模机器学习服务（数千个模型副本处理数百万请求）运行在 Kubernetes 上。

## 安全基础

- 操作系统通过多种机制实施安全：

- **权限**：每个文件都有所有者、组和权限位（所有者、组及其他用户的读/写/执行）。进程以启动它的用户身份（UID）运行，只能访问权限位允许的文件。**root** 用户（UID 0）可以绕过所有权限检查，因此以 root 运行很危险。

- **权限分离**：进程以完成工作所需的最小权限运行。Web 服务器不需要 root 权限；它应以受限用户运行，该用户只能读取 Web 文件并绑定 80 端口。如果服务器被攻破，攻击者的访问能力也只限于这个受限用户能做的事情。

- **沙箱**：在文件权限之外进一步限制进程的行为。**seccomp**（Linux）限制进程可以发起的系统调用；**AppArmor** 和 **SELinux** 定义强制访问控制策略。容器把命名空间、cgroups 和 seccomp 结合起来，形成多层隔离。

- **地址空间布局随机化（ASLR）**：每次程序运行时随机化栈、堆和库的内存位置。这样攻击者更难利用内存损坏 bug（缓冲区溢出），因为他们无法预测代码或数据在内存中的位置。

- 安全是全系统的问题：木桶的强度取决于最薄弱的木板。模型服务系统需要安全的网络通信（TLS/HTTPS）、经过身份验证的 API 访问（API key、OAuth）、输入验证（防止对抗性输入）以及隔离执行（最小权限的容器）。

2. 模拟轮询调度。给定一组带 burst time 的进程，模拟调度过程并计算平均等待时间。
```python
def round_robin(processes, quantum=3):
    """Simulate round-robin scheduling.
    processes: list of (name, burst_time) tuples.
    """
    queue = [(name, burst, 0) for name, burst in processes]  # (name, remaining, wait)
    time = 0
    log = []

    while queue:
        name, remaining, waited = queue.pop(0)
        waited += (time - waited - (processes[[p[0] for p in processes].index(name)][1] - remaining))
        run_time = min(quantum, remaining)
        log.append(f"  t={time:3d}: {name} runs for {run_time} (remaining: {remaining - run_time})")
        time += run_time
        remaining -= run_time

        if remaining > 0:
            queue.append((name, remaining, time))
        else:
            log.append(f"  t={time:3d}: {name} DONE (turnaround: {time})")

    for line in log:
        print(line)

print("Round Robin (quantum=3):")
round_robin([("P1", 10), ("P2", 4), ("P3", 6)], quantum=3)
```

3. 用 LRU 模拟页面置换。给定页面访问序列和固定页框数，统计缺页次数。
```python
def lru_page_replacement(pages, n_frames):
    """Simulate LRU page replacement."""
    frames = []
    faults = 0

    for page in pages:
        if page in frames:
            frames.remove(page)
            frames.append(page)  # move to most recently used
            status = "HIT "
        else:
            faults += 1
            if len(frames) >= n_frames:
                evicted = frames.pop(0)  # remove least recently used
                status = f"MISS (evict {evicted})"
            else:
                status = "MISS (cold)"
            frames.append(page)
        print(f"  Page {page}: {status}  frames={frames}")

    print(f"\nTotal faults: {faults}/{len(pages)} ({faults/len(pages):.0%})")

print("LRU with 3 frames:")
lru_page_replacement([1, 2, 3, 4, 1, 2, 5, 1, 2, 3, 4, 5], n_frames=3)
```
