# 操作系统

*操作系统是硬件与应用程序之间的软件层，负责管理资源、提供抽象并实现隔离。本篇介绍操作系统的职责、进程与线程、CPU 调度、内存管理、文件系统和系统调用。*

- 没有操作系统的计算机，就像没有厨师的厨房：食材和炉灶都在，却没有人安排谁使用炉灶、盘子放在哪里，也没人协调多人共用厨具。**操作系统**负责协调硬件资源，供程序使用。

- 对机器学习从业者来说，操作系统知识有助于理解：为什么 <code>nvidia-smi</code> 会显示各进程的 GPU 内存用量，为什么训练会因“内存不足”而失败，Unix 的 <code>fork()</code> 如何创建进程，以及 Docker 容器如何提供相互隔离的运行环境。

## 操作系统的作用

- 操作系统主要负责三件事：

    - **抽象**：把复杂硬件封装为较易使用的接口。程序可以读写“文件”，而不必关心数据实际位于 SSD、HDD 还是网络驱动器；可以申请“内存”，而不必直接管理物理 RAM。
    - **资源管理**：多个程序共享 CPU、内存、磁盘和网络。操作系统决定由谁使用资源、何时使用以及使用多久。公平而有效的分配策略有助于保持系统响应能力。
    - **隔离与保护**：程序不应任意干扰彼此。例如，浏览器中的错误不应导致内核崩溃，恶意程序也不应读取其他程序的密码。操作系统借助特权级和虚拟内存等硬件机制建立保护边界。

## 进程

- **进程**是正在运行的程序，也是操作系统进行资源管理的基本单位。每个进程都有：

    - **代码**：程序指令，通常映射为只读。
    - **数据**：全局变量和堆上分配的内存。
    - **栈**：函数调用帧和局部变量。
    - **执行状态**：寄存器值、程序计数器、打开的文件等。

- **进程控制块**（PCB）是操作系统用于跟踪进程的数据结构，其中保存进程 ID（PID）、状态、程序计数器、寄存器内容、内存映射、文件描述符和调度优先级等信息。切换进程时，操作系统保存当前进程的执行状态，再恢复下一个进程的状态；这个过程称为**上下文切换**。

- 上下文切换会产生开销：需要保存和恢复寄存器状态，还可能影响缓存和 TLB 的命中情况。开销因处理器和操作系统而异；在同时运行大量进程的系统上，累计成本可能很明显。因此，许多服务器会采用线程或事件驱动模型处理请求，而不是为每个请求都启动一个独立进程。

- Unix 系统通常用 <code>fork()</code> 和 <code>exec()</code> 创建进程：

    - <code>fork()</code> 创建当前进程的子进程。子进程获得父进程地址空间的逻辑副本以及一组文件描述符；现代系统通常用写时复制（copy-on-write）避免立刻复制所有内存。父子进程从 <code>fork()</code> 之后继续执行，但该函数在子进程中返回 0，在父进程中返回子进程的 PID。
    - <code>exec()</code> 用新程序替换当前进程映像。<code>fork()</code> 后，子进程通常调用 <code>exec()</code> 来运行另一个程序。
    - 将创建进程与加载程序分成两个步骤，便于分别配置。在 <code>fork()</code> 和 <code>exec()</code> 之间，子进程可以重定向 I/O、修改环境变量或降低权限。

![进程状态转换：新建→就绪→运行→阻塞/终止，并包含抢占和 I/O 等待](../images/process_states.svg)

- **进程状态**：进程通常处于以下某种状态：
    - **运行**：正在某个 CPU 核心上执行。
    - **就绪**：可以运行，但正在等待 CPU 核心和调度机会。
    - **阻塞**（等待）：必须等某个事件发生才能继续，例如 I/O 完成、获得锁或定时器到期。
    - **终止**：进程已结束，等待父进程收集退出状态。

## 线程

- **线程**是进程内的执行单元。同一进程中的线程共享代码、数据和堆，但各自拥有栈和寄存器状态。

- 多个线程可以直接读写共享内存，因此线程间通信通常较方便。进程也能用管道、套接字或共享内存映射通信；具体开销取决于通信方式，不能一概而论。

- 共享内存也带来风险。若多个线程并发访问同一变量，且至少一个线程在写入，又没有适当同步，就可能发生**竞态条件**：结果取决于线程的执行顺序。这需要用锁等同步机制处理，下一篇会介绍相关内容。

- **内核线程**由操作系统调度器管理，可分别安排到 CPU 核心上运行。创建和切换线程也有资源与调度开销，具体成本取决于操作系统实现。

- **用户线程**（也称绿色线程）由用户态运行时库管理。若多个用户线程映射到单个内核线程，一个用户线程执行阻塞式操作时，进程中的其他用户线程可能也无法运行；若运行时采用多对多映射或异步 I/O，则行为会不同。

- 现代运行时常采用**混合模型**，将多个用户级执行单元映射到较少的内核线程（M:N 模型）。Go 的 goroutine 和 Erlang 的轻量级进程由运行时调度，不是一对一对应的操作系统线程。

- **线程池**预先创建一定数量的线程等待任务到来。新任务会分配给空闲线程，避免为每个任务反复创建和销毁线程。Web 服务器、数据库引擎和机器学习推理服务器都常用线程池。

## CPU 调度

- **调度器**决定每个时刻由哪个进程或线程使用哪个 CPU 核心。常见目标包括提高 CPU 利用率、缩短交互任务的响应时间、提高批处理任务的吞吐量，并兼顾公平性。

- **先到先服务**（FCFS）：按到达顺序运行进程。规则简单，但可能出现**车队效应**：一个长任务会让排在它后面的短任务等待。

- **最短作业优先**（SJF）：先运行估计执行时间最短的任务。若所有作业同时到达，且已知其运行时长，非抢占式 SJF 能最小化平均等待时间；但一般情况下，操作系统无法预先知道准确运行时长。其抢占式版本称为**最短剩余时间优先**（SRTF）：若有剩余执行时间更短的任务到达，就暂停当前任务。

- **轮转调度**（RR）：每个进程获得固定的**时间片**（例如 10 毫秒），时间片用完后被抢占并移到队列末尾。它通常能较快响应交互任务；时间片过短会增加上下文切换，过长则逐渐接近 FCFS。

- **优先级调度**：为每个进程分配优先级，优先运行级别较高的进程。这可能导致低优先级进程长期得不到 CPU，即**饥饿**。**老化**可随等待时间增加进程的优先级，以降低饥饿风险。

- **多级反馈队列**（MLFQ）：设置多个优先级和时间片不同的队列。新进程先进入最高优先级队列；若它用完时间片，通常会被移到优先级较低、时间片较长的队列。交互任务常在耗尽时间片前因等待 I/O 而阻塞，因此往往留在较高优先级队列。MLFQ 可根据任务运行表现调整调度，而不要求预先知道任务类型。

- **完全公平调度器**（CFS）是 Linux 曾采用的经典调度器。它用红黑树按进程的**虚拟运行时间**排序，并优先选择虚拟运行时间较小的进程。教科书中的 CFS 实现模型可用 $O(\log n)$ 时间更新调度数据结构。Linux 较新的内核已引入 EEVDF 等调度机制，因此不能把 CFS 描述当作所有当前版本的实现细节。

## 内存管理

- 操作系统管理物理 RAM，将内存分配给进程，并在不再需要时回收。

- **分页**（第 2 篇介绍过）将虚拟内存划分为固定大小的页，将物理内存划分为页框，再通过页表将页映射到页框。由于页面大小固定，分页避免了外部碎片，但最后一页仍可能产生内部碎片。

- **按需分页**只在页面首次被访问时才将其载入 RAM，而不是在进程启动时加载全部内容。这可以节省内存：例如，程序可能有 1 GB 代码，但一次典型运行中只会访问其中一小部分。

- RAM 已满而又需要载入新页面时，操作系统必须**置换**现有页面。LRU、FIFO 和时钟算法（第 2 篇介绍过）会决定淘汰哪个页面。置换策略不佳会增加缺页异常，严重时还会造成抖动。

- **分段**将内存划分为大小可变的逻辑段，如代码、数据、栈和堆，每段有自己的基址和长度。分段用于逻辑组织和保护；分页则便于物理内存管理。现代系统主要依靠分页进行内存管理，分段的使用较有限。

- **堆**用于存放动态分配的内存，例如 C 的 <code>malloc</code>/<code>free</code>、Java 的 <code>new</code>，以及 Python 中由运行时隐式完成的分配。操作系统向进程提供较大的内存区域，**内存分配器**（如 glibc malloc、jemalloc、tcmalloc）再将其切分为小块。分配器会影响性能：内存碎片会浪费空间，线程间争用也会增加耗时。

## 文件系统

- **文件系统**将 SSD、HDD 等持久化存储组织成由文件和目录构成的层次结构。

- **inode**（索引节点）保存文件元数据，例如大小、所有者、权限、时间戳和数据块位置。目录条目将文件名映射到 inode 编号。因此，同一个 inode 可以对应多个文件名，即**硬链接**。

- **FAT**（文件分配表）是一种常用于 USB 存储设备和 SD 卡的简单文件系统。FAT 表记录每个簇（数据块）之后的下一个簇，从而串起文件内容。它结构简单，但对权限、日志记录和大文件的支持有限。

- **ext4** 是许多 Linux 发行版常用的文件系统。它使用 inode 和 extent（连续数据块范围）管理文件；具体最大文件和卷大小取决于块大小及配置。按常见配置，文件大小上限可达约 16 TB，文件系统卷上限可达约 1 EiB。早期文件系统常用直接、间接和多级间接块指针来定位数据块。

- **日志记录**有助于系统崩溃后恢复文件系统一致性。修改文件系统元数据前，文件系统会先把相关操作写入日志。重新启动时，系统可重放已提交的事务。不同日志模式保护的内容不同；仅有元数据日志并不意味着所有文件数据都已写入持久存储。

- **基于 B 树的文件系统**（如 Btrfs 和 ZFS）用树结构组织数据和元数据，支持高效查找、写时复制快照和校验和等完整性功能。数据库索引也会使用 B 树或其变体。

## 系统调用和内核模式

- **系统调用**是用户程序请求操作系统内核服务的接口。读取文件、申请内存、创建进程或发送网络数据包等操作通常需要系统调用。

- CPU 至少区分以下两种特权级别：
    - **用户模式**：应用程序可执行自己的代码并访问获准的地址空间，但不能直接执行受保护的硬件操作或访问内核数据。
    - **内核模式**：内核可执行特权操作并管理硬件和内存。系统调用提供从用户态受控进入内核的方式。

- 当程序调用 <code>read()</code> 时，流程大致如下：
    1. 程序按调用约定设置参数，并执行系统调用指令或触发陷阱。
    2. CPU 切换到内核态，进入对应的系统调用处理程序。
    3. 内核检查参数、执行 I/O，并在需要时将数据复制到用户缓冲区。
    4. 内核返回用户态，并向程序交还结果。

- 常见系统调用包括：文件操作 <code>open</code>、<code>read</code>、<code>write</code>、<code>close</code>；进程操作 <code>fork</code>、<code>exec</code>、<code>wait</code>、<code>exit</code>；内存操作 <code>mmap</code>、<code>brk</code>；网络操作 <code>socket</code>、<code>bind</code>、<code>listen</code>、<code>accept</code>。

- **中断**是硬件发出的信号，会使 CPU 暂停当前执行并转去处理中断。键盘输入、网络数据包到达和定时器到期都可能产生中断。定时器中断让操作系统有机会暂停当前任务并调度其他任务，从而实现抢占式多任务。

## 网络基础

- 网络栈是操作系统中负责机器间通信的子系统。它有助于理解分布式训练中的梯度同步、模型服务中的请求处理，以及网络延迟对系统性能的影响。

![TCP/IP 协议栈：应用层、传输层、网络层和链路层逐层添加首部](../images/tcp_ip_layers.svg)

- **TCP/IP 模型**将网络通信划分为多个层次，每一层向上一层提供抽象接口：

    - **链路层**：处理单条物理链路上的通信，例如以太网或 Wi-Fi，使用 MAC 地址和帧。
    - **网络层**（IP）：负责跨网络转发数据包。网络接口通过 IPv4 或 IPv6 地址标识；路由器依据目标 IP 地址逐跳转发数据包。
    - **传输层**（TCP/UDP）：为应用程序之间提供端到端通信。
    - **应用层**：包含应用直接使用的 HTTP、DNS 和 gRPC 等协议。

- **TCP**（传输控制协议）提供可靠、有序的字节流传输。建立连接时通常经过三次握手（SYN、SYN-ACK、ACK）；传输时使用序列号和确认，检测丢包并重传，还会通过**拥塞控制**调整发送速率，避免过度占用网络。连接建立和重传可能增加延迟；连接中断时，TCP 也无法保证数据最终一定送达应用程序。

- **UDP**（用户数据报协议）不保证数据送达、顺序或自动重传，也不需要建立连接，因此协议开销通常较小。但实际延迟取决于应用和网络状况。它常用于实时视频、在线游戏和 DNS 等场景；某些 RDMA 互连（如 RoCE v2）会使用 UDP/IP 封装，但这不等于通用 UDP 本身提供 RDMA 语义。

- **套接字**（socket）是操作系统提供的网络通信接口。通信端点通常由 IP 地址、端口号和传输协议共同确定。服务器创建套接字、绑定端口（如 HTTP 常用的 80 端口）、监听并接受连接；客户端连接到服务器后，双方可通过套接字收发数据。

- **DNS**（域名系统）将易读的域名（如 google.com）解析为 IP 地址（如 142.250.80.46）。DNS 是分布式的层次化系统：本地解析器会向根服务器、顶级域服务器和相应域的权威服务器查询或转发请求。

- **HTTP**（超文本传输协议）采用请求—响应模式。客户端发送包含方法、URL、首部和可选消息体的请求，服务器返回状态码、首部和消息体。机器学习模型服务（如 TensorFlow Serving 和 Triton）可通过 HTTP 或 gRPC 提供接口。

- **延迟与带宽**是不同指标。延迟表示数据从源到目的地所需的时间，受物理距离和网络跳数影响；带宽表示单位时间可传输的数据量。卫星互联网可能同时具有高带宽和高延迟，可以传输大量数据，但单次往返仍较慢。分布式训练中，同步屏障通常受延迟影响，因为所有 GPU 都要等待最慢的一方；传输大型梯度张量则更受带宽影响（第 6 章）。

## 虚拟化和容器

- **虚拟化**允许一台物理机运行多个操作系统。**虚拟机监控器**（hypervisor，如 VMware、KVM 和 Xen）创建**虚拟机**（VM），为其提供虚拟 CPU、内存、磁盘和网络接口。每台虚拟机运行自己的客户机操作系统，仿佛拥有专用硬件。

- 虚拟机能提供较强的隔离，也便于在同一台物理机上运行 Linux 和 Windows，或在主机之间迁移虚拟机。由于每台 VM 都运行完整的客户机内核，它通常会占用额外内存和 CPU；实际开销取决于硬件虚拟化支持和工作负载。

![虚拟机在虚拟硬件上运行独立的客户机操作系统；容器共享主机内核，开销更小](../images/container_vs_vm.svg)

- **容器**（Docker、Podman）通常比完整虚拟机更轻。容器不虚拟化整台硬件，而是共享主机内核，并使用内核机制隔离进程：

    - **命名空间**限制进程可见的资源。每个容器可以拥有各自的进程树视图（PID 命名空间）、网络接口、挂载点和主机名。
    - **控制组**（cgroups）限制进程可用的资源，例如 CPU 时间、内存、磁盘 I/O 和网络带宽，避免一个容器耗尽共享资源。

- 容器通常可在较短时间内启动，无需引导完整操作系统。**Dockerfile** 描述基础镜像、依赖项和启动命令。若固定基础镜像版本和依赖，容器有助于在不同环境中复现软件配置；仅有 Dockerfile 并不能保证构建内容永远完全相同。

- 对机器学习来说，容器可将特定版本的 CUDA、cuDNN、PyTorch 和 Python 打包在一起，减少“在我的机器上能运行”的环境差异。AWS SageMaker 和 GCP Vertex AI 等云平台会在容器环境中运行训练任务。

- **Kubernetes**（K8s）负责大规模编排容器工作负载：把 Pod 调度到集群机器上，重启失败的工作负载，根据负载扩缩容，并管理网络。模型服务可用大量副本处理请求。

## 安全基础

- 操作系统通过多种机制实施安全保护：

- **权限**：文件通常关联所有者、所属组和读、写、执行权限位。进程通常以启动它的用户身份运行，并根据权限检查访问文件。Linux 中 root（UID 0）通常拥有广泛权限，但能力机制、强制访问控制等仍可进一步限制它。

- **权限分离**：进程只获得完成任务所需的权限。例如，Web 服务器可用受限账户运行，只能读取所需文件并监听指定端口。即使服务被攻破，攻击者能做的事情也会受到该账户权限限制。

- **沙箱**在文件权限之外进一步限制进程行为。Linux 的 **seccomp** 可过滤进程能调用的系统调用；**AppArmor** 和 **SELinux** 提供强制访问控制策略。容器可结合命名空间、cgroups 和 seccomp 实施多层隔离。

- **地址空间布局随机化**（ASLR）会在程序运行时随机安排栈、堆和库等区域的地址，使攻击者更难预测代码或数据的位置，从而增加利用缓冲区溢出等内存错误的难度。

- 安全需要贯穿整个系统。模型服务应采用安全的网络通信（TLS/HTTPS）、经过身份验证的 API 访问（如 API 密钥或 OAuth）、对不可信输入进行验证，并限制执行环境的权限。

2. 模拟轮转调度。给定一组带有 CPU 执行时间（burst time）的进程，模拟调度并计算平均等待时间。

```python
def round_robin(processes, quantum=3):
    """Simulate round-robin scheduling.
    processes: list of (name, burst_time) tuples.
    """
    queue = [(name, burst, 0) for name, burst in processes]  # (name, remaining, wait)
    time = 0
    log = []

    while queue:
        name, remaining, waited = queue.pop(0)
        waited += (time - waited - (processes[[p[0] for p in processes].index(name)][1] - remaining))
        run_time = min(quantum, remaining)
        log.append(f"  t={time:3d}: {name} runs for {run_time} (remaining: {remaining - run_time})")
        time += run_time
        remaining -= run_time

        if remaining > 0:
            queue.append((name, remaining, time))
        else:
            log.append(f"  t={time:3d}: {name} DONE (turnaround: {time})")

    for line in log:
        print(line)

print("Round Robin (quantum=3):")
round_robin([("P1", 10), ("P2", 4), ("P3", 6)], quantum=3)
```

原代码没有计算或输出平均等待时间；它只记录运行区间和完成时刻，且将完成时刻标为周转时间。若所有进程都在时刻 0 到达，可由“完成时刻减去总执行时间”求每个进程的等待时间，再取平均。代码中更新变量 <code>waited</code> 的公式也不能正确累加等待时间，因此练习描述与实现不一致。

3. 模拟 LRU 页面置换。给定页面访问序列和固定数量的页框，统计缺页次数。

```python
def lru_page_replacement(pages, n_frames):
    """Simulate LRU page replacement."""
    frames = []
    faults = 0

    for page in pages:
        if page in frames:
            frames.remove(page)
            frames.append(page)  # move to most recently used
            status = "HIT "
        else:
            faults += 1
            if len(frames) >= n_frames:
                evicted = frames.pop(0)  # remove least recently used
                status = f"MISS (evict {evicted})"
            else:
                status = "MISS (cold)"
            frames.append(page)
        print(f"  Page {page}: {status}  frames={frames}")

    print(f"\nTotal faults: {faults}/{len(pages)} ({faults/len(pages):.0%})")

print("LRU with 3 frames:")
lru_page_replacement([1, 2, 3, 4, 1, 2, 5, 1, 2, 3, 4, 5], n_frames=3)
```

该实现把最近最少使用的页面放在列表开头，并在命中时将页面移到末尾，因此在页框数为正数、访问序列非空的前提下，可按 LRU 规则统计。
