# 大规模基础设施

*服务数百万用户所需的系统，不能只依靠一台服务器。本文介绍可扩展性模式、分布式系统基础、微服务、数据管道、数据库扩展、搜索与向量系统、可观测性、可靠性工程和 CI/CD。*

- 每秒处理 1 个请求的模型可以在笔记本上运行；每秒处理 10 万个请求并满足 99.9% 可用性目标，则需要分布式系统、自动故障切换和精心设计的数据管道。这些是从小规模原型扩展到大规模服务时常见的设计问题。

## 可扩展性

- **垂直扩展（scale up）**：换用更强的机器，增加 CPU、RAM 或 GPU。实现简单，但受单机上限限制，也会形成单点故障。
- **水平扩展（scale out）**：增加机器，让每台处理一部分流量。它不受单机容量限制，但需要负载均衡（第 1 篇）、数据分区和分布式状态管理。
- **无状态服务**通常容易水平扩展：在负载均衡器后增加实例即可。若推理服务器在启动时加载模型权重，之后独立处理每个请求，且不在本地保留跨请求状态，任一实例都可以接手请求。
- **有状态服务**（数据库、KV cache、特征库）更难扩展。状态需要跨机器分区（第 1 篇的分片）并复制，以应对故障。
- **可扩展性关系**：对拥有 $n$ 台服务器的系统：
    - **理想情况**：吞吐量随服务器数线性增长（$n$ 台服务器 → $n$ 倍吞吐量）。
    - **实际情况**：协调、负载均衡和数据传输开销会使吞吐量次线性增长。第 13 章的阿姆达尔定律也适用：串行部分（共享状态、协调）限制总体加速比。

## 分布式系统

- **分布式系统**由多台机器协作提供服务，常见难点包括：
- **网络分区**：机器之间可能无法通信，例如网线断开、交换机故障或数据中心断电。系统必须应对部分节点失联。
- **时钟偏差**：不同机器的时钟可能不一致。机器 1 在 10:00:01 记录事件 A，机器 2 在 10:00:01 记录事件 B，不代表两件事同时发生。**逻辑时钟**（Lamport 时间戳、向量时钟）可在不依赖物理时钟的情况下确定部分事件顺序。
- **共识**：多台机器如何对一个值达成一致，例如决定谁是领导者？**Raft** 是常见的共识算法。集群选出领导者，由其处理写入；领导者故障后，其余节点重新选举。通常需要多数派才能继续服务，例如 5 个节点中至少 3 个，因此在相应假设下可容忍 $\lfloor(n-1)/2\rfloor$ 个节点故障。
- **分布式锁**：协调多台机器，避免同时执行某个关键操作。**Redlock** 是基于多个 Redis 实例的分布式锁算法：若多数实例授予锁，客户端就认为获得了锁。它可用于减少重复部署模型或多个训练任务同时写检查点的风险；锁的正确性仍取决于时钟、租约、暂停和网络故障等假设，应按一致性要求评估。

## 微服务

![机器学习微服务架构：API 网关把请求路由到特征、模型和日志服务；各服务连接自己的数据库，并通过消息队列通信](../images/microservices_architecture.svg)

- **微服务**将系统拆分为小型、可独立部署的服务，每个服务负责一个业务领域：

```
┌─────────────┐  ┌──────────────┐  ┌─────────────┐
│ API 网关    │→ │ 特征服务     │→ │ 特征数据库  │
└─────────────┘  └──────────────┘  └─────────────┘
       │
       ├────────→ ┌──────────────┐  ┌─────────────┐
       │          │ 模型服务     │→ │ 模型存储    │
       │          └──────────────┘  └─────────────┘
       │
       └────────→ ┌──────────────┐  ┌─────────────┐
                  │ 日志服务     │→ │ 日志存储    │
                  └──────────────┘  └─────────────┘
```

- **优点**：可独立部署（更新模型服务而不改动特征服务）、独立扩缩容（按请求量扩模型服务器，按特征读取量扩特征服务器），并可为不同服务选择适合的技术栈（例如模型服务用 Python、特征服务用 Go）。
- **缺点**：网络调用会增加往返开销；跨服务调试更复杂；多个服务间的数据一致性难以通过单个事务保证。
- **服务发现**：API 网关如何找到模型服务？常见方式有基于 DNS 注册服务名、使用 Kubernetes Service，或采用 Consul、Eureka 等服务注册表。
- **Saga 模式**：当一个操作横跨多个服务（例如创建用户、分配资源、发送欢迎邮件）时，可将其拆成一系列本地事务；若某步失败，则执行相应的补偿操作。Saga 不等同于跨服务的原子事务。

## 数据管道

- 机器学习系统需要摄取大量数据。**数据管道**负责传输、转换和提供这些数据：

### 批处理

- 按固定时间间隔（例如每小时或每天）处理大量数据。
- **MapReduce**：早期批处理范式，依次执行 Map（独立转换每条记录）、Shuffle（按键分组）和 Reduce（对每组聚合）。概念简单，但编写起来较繁琐。
- **Apache Spark**：常见的批处理引擎，支持内存计算、SQL、DataFrame 和机器学习管道。迭代算法在某些负载下可比 MapReduce 快很多；原文举出的 100 倍不是普遍加速比例。Spark 常用于大规模特征工程。
- **示例**：为推荐系统计算用户特征。输入为过去 30 天的 10 亿条用户行为事件，输出为 1 亿个用户特征向量；每天运行 Spark 作业，再写入特征库。实际耗时取决于数据量、集群规模和特征计算。

### 流处理

- 数据到达时实时处理，目标可以是亚秒级延迟。
- **Apache Flink**：常用于流处理，可支持事件时间、窗口计算（滚动、滑动、会话窗口）和端到端精确一次语义；精确一次需要正确配置检查点、数据源与接收端。
- **Kafka Streams**：内嵌在 Kafka 生态中的流处理库，可在不另建处理集群的情况下执行较简单的过滤和聚合。
- **示例**：实时欺诈检测。信用卡交易作为 Kafka 事件进入 Flink 作业，作业计算交易频率、地点变化等滚动统计并标记异常。原文所举的 100 ms 是延迟目标示例，需按系统测试确认。

### Lambda 架构

- **Lambda 架构**将批处理与流处理结合：**批处理层**提供准确、完整但有延迟的结果；**速度层**提供近实时的近似结果；**服务层**合并两者的输出。
- 许多团队也采用 **Kappa 架构**，把流作为数据事实来源。若事件日志能够重放，就可以通过重放事件重新计算结果，减少单独维护批处理路径的需求。此处的 Lambda 架构与 AWS Lambda 函数服务无关。

## 机器学习训练基础设施

- 训练 100B 以上的大模型是大型基础设施工程：需要许多 GPU 长时间协作，消耗大量电力、生成海量数据并产生高额费用。基础设施会影响训练能否稳定完成。

### GPU 集群

- 训练集群由通过高速网络互连的 GPU 服务器组成，主要部件包括：

![GPU 集群示意：每个节点的 8 张 GPU 通过 NVLink 互连，节点之间使用胖树 InfiniBand 网络；集群规模从 64 张扩展到 16000 张以上 GPU](../images/gpu_cluster_topology.svg)

- **GPU 服务器（节点）**：每台服务器常配 4–8 张 GPU。一个示例配置是 8 张 H100、2 颗 AMD EPYC CPU、2 TB RAM 和 30 TB NVMe SSD。H100 的 NVLink 总带宽最高约 900 GB/s（具体取决于连接和统计口径），显著高于单条 PCIe 链路；“30 倍”比较取决于 PCIe 代际和是否按聚合带宽计算。
- **集群规模**：小型训练集群可能有 64–256 张 GPU（8–32 个节点）；大规模训练可用数千至数万张 GPU。原文列举 Meta 的 Llama 3 使用 16,384 张 H100、Google TPU pod 使用 8,000 多颗芯片，均是具体项目配置，不代表所有模型训练所需规模。
- **粗略成本估算**：原文估计训练 70B 模型的计算费用约 200 万美元，训练 400B 以上模型约 5000 万至 1 亿美元。若按每张 H100 3 万美元估算，16,000 张卡的硬件成本约 4.8 亿美元。这些数字受训练令牌数、集群利用率、租赁价格与设备代际影响，仅供量级参考。

### 网络拓扑

- GPU 节点之间的网络会影响分布式训练效率。若 GPU 交换梯度的速度跟不上计算，设备就会等待通信。
- **InfiniBand** 常用于 GPU 集群互连。NVIDIA Quantum-2 InfiniBand 每个端口可达 400 Gb/s；若每节点使用 8 个端口，理论总链路带宽约 400 GB/s。它不是可直接保证的二分带宽，实际值取决于拓扑、超额订阅和通信模式。
- **RDMA（远程直接内存访问）**可在节点间传输数据而减少 CPU 参与。若还要让网络适配器直接访问 GPU 内存，需要支持相应的 GPUDirect RDMA 路径。原文以 TCP 约 100 μs、RDMA 约 1 μs 举例；实际延迟受硬件、消息大小和配置影响。
- **网络拓扑很重要**：无超额订阅的**胖树（Clos）**网络可提供较高的任意节点间通信带宽。成本较低的 rail-optimized 或 3D torus 拓扑可能带宽较低。拓扑要匹配并行方式：
    - **数据并行**：GPU 间执行 all-reduce，通常需要较高的二分带宽。
    - **张量并行**：通信主要发生在节点内，可由 NVLink 承担。
    - **流水线并行**：主要在相邻阶段间传输激活值，可重点优化特定节点对之间的带宽。
- **以太网方案**：**RoCE v2**（融合以太网上的 RDMA）可在以太网基础设施上支持 RDMA；与 InfiniBand 相比，成本和延迟、拥塞表现会随设备及网络配置变化。原文列举 Google 在部分 TPU 网络中使用 RoCE；Ultra Ethernet Consortium 正在推动面向 AI 工作负载的以太网技术。

### 训练存储

- 训练通常需要三类存储：
    - **数据集存储**：保存 1–100 TB 的文本或 PB 级多模态数据，可使用分布式文件系统或对象存储。数据加载器通常需要连续读取高吞吐数据。Lustre、GPFS 是常见 HPC 文件系统；云端也可使用 AWS FSx for Lustre、GCP Filestore 等服务。
    - **检查点存储**：定期保存模型权重、优化器状态和调度器状态。70B 模型的 Adam 两组 FP32 优化器矩估计本身约需 $70B\times4\text{ bytes}\times2=560$ GB；这不包括约 140 GB 的 FP16 模型权重以及可能保存的主权重等状态。因此，“560 GB 检查点”不是完整检查点的通用大小。若每小时保存 560 GB、连续 3 个月且保存约 2000 份，仅这部分就约 1.1 PB；实际系统通常只保留最近若干份并清理旧文件。检查点写入速度也会影响训练停顿。
    - **日志和指标**：记录损失曲线、学习率和梯度范数等实验跟踪数据。体积相对较小，但通常需要持续写入；可使用 W&B、MLflow 或 TensorBoard。
- **存储瓶颈**：原文估计 16,000 张 GPU 组成的集群需要持续读取约 100 GB/s 的训练数据。若文件系统无法提供足够吞吐，GPU 可能等待数据。预取、缓存以及使用 WebDataset、Mosaic Streaming 等优化数据格式的工具有助于提高输入效率。

### 作业调度

- 一个 GPU 集群通常由多个团队和项目共用。**作业调度器**负责把 GPU 分配给训练作业：
- **SLURM**：常见 HPC 作业调度器。用户提交 GPU 数量、内存和时间限制等需求；SLURM 管理队列和资源，可按优先级调度、抢占作业并在团队间实行公平共享。
- **带 GPU 调度的 Kubernetes**（第 18 章第 2 篇）：云原生方案。GPU device plugin 把 GPU 暴露为可调度资源；Volcano 和 Run:ai 等工具增加 gang scheduling（一次分配作业所需的全部 GPU）、优先级队列和 GPU 共享等功能。
- **调度难点**：
    - **碎片化**：1000 张 GPU 中可能有 200 张空闲，但分散在 50 个节点上（每节点空闲 4 张）。需要 128 张互连 GPU 的作业可能无法启动。可通过迁移作业整理空闲资源，或按网络拓扑分配 GPU。
    - **优先级与抢占**：紧急实验可能需要抢占低优先级作业；但中断运行两天的训练会浪费上次检查点以来的计算。调度器需要权衡优先级和资源效率。
    - **公平共享**：长期来看，各团队应获得分配给自己的计算资源份额，即使某个团队提交的作业数量更多。

### 容错

- 数千张 GPU 连续运行数月时，硬件故障需要纳入正常设计。16,000 张 GPU 集群的平均故障间隔可能以小时计，但实际故障率取决于设备、环境和统计口径。
- **常见故障**：GPU 可纠正或不可纠正的内存错误、节点内 NVLink 故障、节点间 InfiniBand 链路故障、内核崩溃或电源故障，以及磁盘或存储控制器故障。
- **检查点**是主要恢复手段。每隔若干训练步保存模型、优化器和数据加载位置。故障后识别并移除故障节点，再从最近的检查点恢复；损失的计算量取决于故障距上次检查点的时间。
- **检查点频率的取舍**：更频繁地保存（例如每 10 分钟）可减少故障时丢失的计算，但会增加保存开销；不频繁保存（例如每 2 小时）开销较低，却可能损失近 2 小时的计算。每 20–60 分钟保存一次是原文给出的示例，不是通用规则。
- **弹性训练**：PyTorch Elastic、DeepSpeed 等框架可在部分节点故障时重新组织工作进程或从检查点恢复。若 500 个节点中有 2 个故障，作业能否缩到 498 个节点继续运行，取决于框架、通信后端、训练状态和调度器，不应假定所有配置都能无缝继续。
- **健康监控**：持续监测 GPU 温度、内存错误和吞吐量，网络丢包与延迟，以及存储吞吐和错误率。部分集群会定期运行简短计算任务，提前发现性能退化的设备。
- **大规模案例**：Meta 曾报告 Llama 3 使用 16,384 张 H100 训练 54 天，发生约 466 次作业中断，实际有效训练时间约占墙钟时间的 90%。这是一个案例，具体故障率和恢复效率不能推广到所有集群。

### 成本与效率

- 训练基础设施的费用以 GPU 使用时间为主。原文给出的成本比例是估算值，会随集群建设、租赁方式和会计口径变化：

| 组件 | 总成本估计占比 |
|-----------|----------------|
| GPU 计算 | 70–80% |
| 网络（InfiniBand） | 10–15% |
| 存储 | 5–10% |
| 制冷与电力 | 5–10% |

- **GPU 利用率（模型浮点运算利用率，MFU）**衡量有效计算量占理论峰值的比例。峰值要按精度确定：H100 稠密 FP16/BF16 Tensor Core 峰值约 989 TFLOPS，FP8 约 1,979 TFLOPS；若计入结构化稀疏加速，标称值会更高。MFU 分母应与训练所用精度、是否计入稀疏保持一致。原文把 40–50% 称为“良好”、50–60% 称为“优秀”，只能作为经验参考。通信、内存带宽、检查点和数据加载都会拉低 MFU。
- **提高 MFU**：重叠计算与通信（第 6 章）、采用高效注意力（FlashAttention，第 16 章）、优化数据加载以避免 GPU 等待数据，并用异步检查点先写高速 NVMe、再后台复制到持久存储。
- **自建还是租用**：原文给出的经验是，小规模（少于 256 张 GPU）云服务可能更便宜，因为无需前期购置；大规模（超过 1000 张 GPU 且持续使用 6 个月以上）自建硬件的三年总拥有成本可能低约 2–3 倍。实际盈亏点取决于利用率、资本成本、电力、维护、供应能力和云端折扣。

## 数据库扩展

- **只读副本**：把读取请求分配给主数据库的副本；主库处理写入，副本处理读取。读多写少的系统可通过副本扩展读取能力，但复制延迟和主库瓶颈会影响线性扩展。
- **分区（分片，第 1 篇）**：把数据拆到多个数据库中，分别处理读写。跨分片查询（例如连接不同分片的数据）会更复杂。
- **连接池**：数据库可处理的并发连接数量有限。PgBouncer 等连接池复用 PostgreSQL 连接，避免许多服务实例同时创建连接导致耗尽。

## 搜索与向量系统

### 文本搜索

- **倒排索引**为每个词保存包含该词的文档列表。查询时合并或求交各查询词对应的列表。Elasticsearch 是常用的分布式实时搜索引擎，支持全文检索、聚合和地理空间查询。
- **BM25** 是常见的文本检索评分函数，会综合词频、逆文档频率和文档长度归一化。它结构简单，在关键词匹配占主导的查询中仍有竞争力。

### 向量搜索

- **向量数据库**保存嵌入（高维向量），并执行快速的**近似最近邻（ANN）**搜索。给定查询向量，系统寻找最相似的 $k$ 个已存向量。
- **FAISS**（Facebook AI Similarity Search）是向量检索库，不是数据库，支持多种索引：
    - **Flat**：精确扫描，复杂度 $O(n)$，可用于小数据集或作为基准结果。
    - **IVF（倒排文件索引）**：先将向量聚类，再只搜索较近的若干簇。若簇大小均衡、每次只探测少量簇，查询量可能接近 $O(n/k)$；实际复杂度取决于簇数和探测数量。
    - **HNSW（分层可导航小世界）**：图搜索方法，通过分层图由粗到细地查找。它在不少场景中速度和召回率表现良好，但内存、查询延迟和准确度需按应用调优，不存在对所有任务都最优的默认索引。
    - **乘积量化（PQ）**：把向量压缩为紧凑编码以减少内存，需权衡召回率与压缩率。
- **托管向量数据库**：Pinecone、Weaviate、Milvus、Qdrant 等实现可提供扩展、复制和实时更新能力；FAISS 本身不会管理完整数据库服务。
- **RAG（检索增强生成）**：先用文本编码器将用户查询转成向量，再从向量索引检索相关文档，并把文档加入 LLM 提示词。检索相关性会影响最终回答，但回答质量也取决于生成模型和提示设计。

## 可观测性

- **可观测性**指通过系统对外产生的数据理解其内部运行情况，常按三类信号组织：

### 日志

- **结构化日志**（如 JSON）便于检索和解析；自由文本日志较难自动处理。常记录时间戳、服务名、请求 ID（用于跨服务追踪）、严重级别和相关上下文。
- **ELK 栈**（Elasticsearch、Logstash、Kibana）：常见日志处理链路。Logstash 收集并转换日志，Elasticsearch 建立索引，Kibana 用于搜索和可视化。

### 指标

- **指标**是随时间记录的数值，例如请求率、错误率、延迟分位数、GPU 利用率和队列深度。Prometheus 可从服务抓取指标，Grafana 用于仪表盘和告警。
- **RED 方法**面向服务：**R**ate（请求率）、**E**rrors（错误率）、**D**uration（延迟）。可为每个服务监控这三项。
- **USE 方法**面向资源：**U**tilisation（利用率）、**S**aturation（饱和度，例如队列深度）、**E**rrors（错误数）。可用于 CPU、GPU、内存、磁盘和网络。

### 分布式追踪

- **分布式追踪**记录一个请求经过多个服务的完整路径。例如 API 网关 → 特征服务 → 模型服务 → 后处理服务。每个 **trace（追踪）**包含各环节耗时，可用于定位延迟来源。
- **OpenTelemetry** 是追踪、指标和日志的开放标准。代码埋点可导出到 Jaeger、Zipkin、Datadog 等后端。

## 可靠性

- **SLO（服务等级目标）**：系统设定的可靠性目标，例如“99.9% 的请求在 200 ms 内完成”。若这是按请求计数的延迟目标，错误预算是未达标请求比例；不能直接换算为停机分钟数。
- **SLI（服务等级指标）**：衡量 SLO 的指标，例如过去 5 分钟的第 99 百分位延迟。
- **SLA（服务等级协议）**：与客户签订、未达成时会产生后果的承诺，例如可用性低于 99.95% 时给予服务抵扣。
- **错误预算**：若以一个月 30 天的时间可用性衡量，99.9% 可用性对应约 43 分钟不可用时间；若按请求延迟或错误率衡量，预算则按请求计算。SLO 超额完成时，团队可在预算内进行风险变更；预算耗尽时可优先处理可靠性问题。
- **混沌工程**：主动注入故障（关闭服务器、增加网络延迟或模拟数据损坏），验证系统能否正确应对。Netflix 的 Chaos Monkey 会随机终止生产实例。测试应在受控范围内执行，并根据结果改进系统。

## CI/CD

- **持续集成（CI）**：每次代码变更都自动构建并验证。每次提交可触发 lint、类型检查、单元测试和集成测试；未通过时阻止合并或发布。
- **持续部署（CD）**：通过 CI 的变更自动部署。常见策略包括：
    - **蓝绿部署**：维护两套相同环境，蓝色运行当前版本，绿色运行新版本；验证后切换流量。若绿色环境失败，可切回蓝色版本，回滚速度取决于流量和状态迁移方式。
    - **金丝雀部署**：先把少量流量（例如 1–5%）送到新版本，监控指标正常后逐步扩大，以限制故障影响范围。
    - **功能开关**：部署新代码但先隐藏功能，再按内部测试、Beta 用户到所有用户的顺序启用。这样可以把代码部署与功能发布分开。
- **机器学习 CI/CD**还包括模型验证步骤，例如检查张量形状、梯度与评估集表现，在影子部署中并行运行新旧模型比较输出，再从 1% 逐步扩大到全部流量。评估集和发布门槛应按任务设定。
