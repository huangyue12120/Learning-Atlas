# 大规模基础设施

*构建服务于数百万用户的系统需要超过单台服务器。本文件涵盖了可扩展模式、分布式系统基础、微服务、数据管道、数据库扩缩、搜索和向量系统、可观测性工程、可靠性工程以及CI/CD流程*

- 每秒处理1个请求的模型可以在笔记本上运行。每秒处理10万次请求且保持99.9%可用性的系统需要分布式系统、自动故障转移和精心设计的数据管道。本文件涵盖了这些模式之间的桥梁。

## 可扩展性

- **垂直扩缩**（垂直扩展）：获取更大的机器。更多CPU、更多RAM和更大GPU。简单但有硬限制（最大的可用机器）且只有一个单点故障。

- **水平扩缩**（水平扩展）：添加更多的机器。每个负责一部分流量。没有单台机器的限制，但需要：负载均衡（文件01）、数据分区和处理分布式状态。

- **无状态服务**默认是水平可扩缩的。在负载均衡器后面添加更多实例。一个模型推理服务器，在启动时加载权重并独立处理请求，是无状态的——任何实例都可以处理任何请求。

- **状态化服务**（数据库、KV缓存、特征存储）更难扩展。状态必须在机器之间分区（分片、文件 01），并进行故障恢复复制。

- **系统可扩展性方程**：对于具有 $n$ 台服务器的系统：
    - **理想情况**：吞吐量线性增长（$n$ 台服务器 → $n\times$ 吞吐量）。
    - **实际情况**：协调、负载均衡和数据传输带来的开销导致吞吐量非线性增长。阿姆拉定律（第 13 章）适用：共享状态和协调的串行部分限制了加速速度。

## 分布式系统

- 一个**分布式系统**是由多台机器组成的，它们协同工作以提供服务。其基本挑战包括：

- **网络分区**：机器无法始终通信。例如，电缆被切断、交换机故障或数据中心失去电力。系统必须处理部分失败情况。

- **时钟偏移**: 不同的机器有不同的时钟。"事件A在机器1上发生于10:00:01"和"事件B在机器2上发生于10:00:01"并不意味着它们同时发生。**逻辑时钟**（如Lamport时间戳或向量时钟）通过不依赖物理时钟来建立顺序关系。

- **一致性**: 多个机器如何达成一致（例如，谁是领导者？）**Raft**是标准的一致性算法。一个节点集群选举一个领导者。领导者处理所有写操作。如果领导者失败，剩余的节点会选举一个新的领导者。需要超过半数（3/5个节点）才能正常运行，因此它能容忍$\lfloor(n-1)/2\rfloor$故障。

- **分布式锁**：确保只有一个机器执行关键操作。 **Redlock**（基于Redis）在多个Redis实例之间获取锁。如果大多数实例授予了锁，则已获得。用于：防止重复模型部署，确保只有一个训练作业写入检查点。

## 微服务

![](../images/microservices_architecture.svg)


- **微服务**将系统分解为小的、独立可部署的服务。每个服务拥有一个领域：

```
┌─────────────┐  ┌──────────────┐  ┌─────────────┐
│ API Gateway │→ │ Feature Svc  │→ │ Feature DB  │
└─────────────┘  └──────────────┘  └─────────────┘
       │
       ├────────→ ┌──────────────┐  ┌─────────────┐
       │          │ Model Svc    │→ │ Model Store │
       │          └──────────────┘  └─────────────┘
       │
       └────────→ ┌──────────────┐  ┌─────────────┐
                  │ Logging Svc  │→ │ Log Store   │
                  └──────────────┘  └─────────────┘
```

- **优势**：独立部署（更新模型服务而不影响特征服务），独立缩放（根据请求负载缩放模型服务器，根据特征存储读取率缩放特征服务器），技术自由（模型服务使用Python，特征服务使用Go）。

- **劣势**：网络开销（每个服务调用都是一个网络往返），复杂性（调试跨越多个服务），数据一致性（没有跨服务事务）。

- **服务发现**：API网关如何找到模型服务？选项：基于DNS（每个服务注册一个DNS名称），K8s服务（内置），或服务注册中心（Consul，Eureka）。

- **Saga模式**：对于跨越多个服务的操作（创建用户 + 分配资源 + 发送欢迎邮件），使用Saga：一系列本地事务及其补偿动作，如果任何步骤失败。

## 数据管道

- ML系统消耗大量数据。 **数据管道**移动、转换和提供此数据：

### 批处理处理

- 按固定时间间隔（每小时，每日）处理大量数据。

- **MapReduce**：原始批处理范式。映射（独立地变换每个记录）→洗牌（按键分组）→聚合（按组聚合）。概念上简单但实现起来冗长。

- **Apache Spark**：现代批处理引擎。内存处理（100倍快于MapReduce，适用于迭代算法）。支持SQL、数据框和ML管道。大规模特征工程的标准工具。

- **示例**：为推荐系统计算用户特征。输入：过去30天的1B个用户活动事件。输出：100M个用户特征向量。每天运行一个Spark作业，将结果输出到特征存储中。

### 流处理

- 在数据到达时实时处理数据（亚秒级延迟）。

- **Apache Flink**：流处理引擎的领先者。保证 Exactly-once处理，事件时间处理（按事件发生的时间处理，而不是按事件到达的时间），窗口处理（滚动、滑动和会话窗口）。

- **Kafka Streams**：内置在Kafka中的轻量级流处理。适用于简单的转换（过滤、聚合）而不需部署单独的集群。

- **示例**：实时欺诈检测。每个信用卡交易都是一个Kafka事件。一个Flink作业计算运行统计（交易频率、位置变化）并在100毫秒内标记异常。

### Lambda架构是一种分布式系统设计模式，它将数据处理任务分解为多个小的、独立的组件。这些组件可以并行运行，以提高系统的吞吐量和响应时间。Lambda架构的核心思想是使用微服务来构建系统，并通过事件驱动的方式来协调各个组件之间的交互。

- 将批处理和流式处理结合起来。**批处理层**提供准确、全面的结果（但有延迟）。**速度层**提供近似实时的结果。一个**服务层**将两者合并。

- 实际上，许多团队现在使用 **Kappa 架构**：仅进行流处理，将流视为真理的来源。由于 Kafka 保留事件，因此可以通过重新播放流来模拟批处理操作。

## ML 训练基础设施

- 训练一个前沿模型（数百万参数）是一个大型基础设施问题：成千上万的GPU运行数月，消耗兆瓦级电力，产生PB级数据，并花费数十亿美元。基础设施决定了训练是否成功或失败。

### GPU集群

- 训练集群是由连接高速网络的GPU服务器组成的集合。关键组件：

![](../images/gpu_cluster_topology.svg)


- **GPU服务器（节点）**：每个服务器有4到8个GPU。典型的配置是8个H100 GPU，2个AMD EPYC CPU，2TB内存，30TB NVMe SSD。这些GPU在同一个节点内通过**NVLink**连接（H100上的每块GPU为900GB/s），比PCIe快30倍。

- **集群大小**：一个小型训练集群包含64到256个GPU（8到32个节点）。一个前沿模型训练集群包含4,000到32,000个GPU（500到4000个节点）。Meta的Llama 3使用了16,384个H100 GPU。Google在TPU pod中使用了8,000+芯片。

- **后背纸张**：训练一个70B模型大约需要~$2M in compute. Training a 400B+ frontier model requires ~$50-100M。集群硬件本身的价格大约是H100价格的~$500M-$1B（$30K per GPU × 16,000 GPUs = $480M）。

### 网络拓扑结构

- GPU节点之间的网络是最重要的基础设施组件。如果GPU不能以足够快的速度交换梯度，它们就会闲置等待通信完成。

- **InfiniBand** 是 GPU 集群网络的标准。NVIDIA 的 **Quantum-2 InfiniBand** 提供每端口 400 Gb/s。每个节点通常有 8 个 InfiniBand 端口（一个对应于 GPU），总共每个节点提供 400 GB/s 的总双向带宽。

- **RDMA**（远程直接内存访问）：InfiniBand支持RDMA，它将GPU内存从不同节点直接传输到另一个节点，而无需CPU参与。这将延迟从~100μs（TCP）减少到~1μs，并且对于高效的梯度所有者广播（第6章）至关重要。

- **网络拓扑结构很重要**：Clos网络（胖树）提供全带宽（任何GPU都可以以最高速度与任何其他GPU通信）。成本较低的拓扑结构（铁路优化、3D torus）提供较少的带宽但成本更低。拓扑结构必须匹配并行策略：
    - **数据并行**：所有GPU之间的广播（all-reduce）需要高带宽（胖树）。
    - **张量并行**：节点内部的通信由NVLink处理（不需要网络）。
    - **流水线并行**：相邻流水线阶段之间的通信仅需要特定节点对之间的带宽（铁路优化是可行的）。

- **以太网替代方案**：RoCE v2（RDMA over Converged Ethernet）在标准以太网基础设施上提供RDMA。虽然比InfiniBand便宜，但延迟更高且更易出现拥塞。谷歌使用RoCE为某些TPU pod网络进行通信。Ultra Ethernet Consortium正在开发用于AI工作负载的无损以太网。

### 训练中的存储

- 训练需要三个存储层级：

    - **数据存储**：训练语料库（1-100 TB的文本，或PB级多模态数据）。存储在分布式文件系统或对象存储中。必须支持高吞吐量顺序读取（数据加载器以大批次读取数据）。Lustre和GPFS是常见的HPC文件系统；云替代方案包括AWS的**FSx for Lustre**和GCP的**Filestore**。

    - **检查点存储**：训练状态（模型权重+优化器状态+调度器状态）定期保存。对于一个70B混合精度模型，Adam优化器每次大约需要560 GB的存储空间（70B × 4字节 × 2个优化器）。每运行3个月保存一次检查点 = ~2000个检查点 = 1.1 PB。实践中，只保留最新的N个检查点，并删除旧的。必须足够快，以确保检查点化不会显著减慢训练速度。

    - **日志和指标**：实验跟踪数据（损失曲线、学习率调度、梯度范数）。相对较小但必须实时写入。W&B、MLflow或TensorBoard处理这些内容。

- **存储瓶颈**：一个包含16,000个GPU的集群加载训练批次时，需要连续读取约100 GB/s的数据。如果文件系统无法支持这种吞吐量，GPU会空闲等待数据。数据管道优化（预取、缓存、使用WebDataset或Mosaic流式传输格式进行优化）至关重要。

### 作业调度

- GPU集群为多个团队和项目服务。作业调度器分配GPU给训练作业：

- **SLURM**：标准的HPC作业调度器。用户提交作业指定GPU数量、内存和时间限制。SLURM分配资源并管理队列。支持优先级调度、抢占式调度和团队间的公平共享分配。

- **Kubernetes with GPU scheduling** (第18章文件02): 云原生方法。K8s GPU设备插件将GPU作为可调度资源暴露出来。**Volcano**和**Run:ai**添加了ML-specific调度特性：gang调度（一次性分配所有GPU，而不是逐个），优先级队列以及GPU时间共享。

- **调度挑战**：
    - **碎片化**: 一个拥有1000个GPU的集群可能有200个空闲GPU，但分布在50个节点上（每个节点4个空闲）。一个需要128个连续GPU的任务无法运行，尽管总共有足够的GPU。**碎片化**（迁移任务以合并空闲GPU）或**拓扑感知调度**（分配连接良好的GPU）解决这个问题。
    - **优先级和抢占**: 紧急实验应该抢占较低优先级的任务。但 preempt一个已经运行了2天的训练任务浪费了计算资源。调度器必须平衡优先级与效率。
    - **公平分享**: 团队应该在一段时间内获得其分配的计算资源，即使团队提交了超过其份额的任务。

### 故障恢复

- 在数千个GPU运行数月的情况下，硬件故障并不是罕见现象——它们是常规的。一个拥有16,000个GPU的集群的平均故障间隔时间（MTBF）测量在小时级，而不是月级。

- **常见故障**：GPU内存错误（ECC可纠正和不可纠正），NVLink失败（同一节点内的GPU-to-GPU通信），InfiniBand链路失败（节点间通信），节点崩溃（内核panic、电源供应器故障）以及存储故障（硬盘或控制器故障）。

- **检查点**是主要防御措施。每N步保存完整的训练状态（模型、优化器、数据加载器位置）。在失败时：识别出失败的节点，替换或移除它，从最新的检查点重新开始训练。故障的成本是从最后一次检查点到失败之间的计算量。

- **检查点频率交易**：频繁的检查点（每10分钟一次）在失败时浪费较少的计算资源，但训练速度较慢（560 GB的检查点需要时间）。不频繁的检查点（每2小时一次）更快，但在失败时浪费最多2小时的计算资源。大多数团队每20-60分钟进行一次检查点。

- **弹性训练**：现代框架（PyTorch Elastic、DeepSpeed）支持在不重启的情况下调整训练运行。如果从500个节点中有2个失败，训练将继续使用498个节点。失败的节点被替换，并且当它们再次上线时，自动将其纳入训练过程中。

- **健康监控**：持续监测所有GPU（温度、内存错误、计算吞吐量）、网络链接（丢包率、延迟）和存储（吞吐量、错误率）。自动在异常时发出警报。某些集群会定期运行GPU健康检查（一个短的计算测试），以提前识别硬件退化，防止其失败。

- **在大规模上**：训练 Meta 的 Llama 3（16,384 H100s，54 天）经历了 ~466 次作业中断。有效训练时间仅为墙钟时间的 ~90% —— 10% 被失败和恢复所消耗。实现 90%（而不是 50% 或 70%）所需的基础设施是那些能够训练前沿模型的组织与那些不能的关键区别。

### 成本与效率

- 训练基础设施成本主要由GPU小时数决定：

| 组件 | 总成本百分比 |
|-----------|----------------| GPU 计算 | 70-80% |
| 网络（InfiniBand） | 10-15% |
| 存储 | 5-10% |
| 冷却和电力 | 5-10% |

- GPU利用率（模型FLOPs利用率，MFU）衡量了GPU实际用于有用计算的理论峰值性能所占的比例。H100的峰值是989 TFLOPS（FP8）。达到40-50%的MFU是好的；50-60%是优秀的。差距主要由：通信开销（所有reduce、管道气泡）、内存带宽限制以及在检查点和数据加载期间的空闲时间所造成。

- **提升MFU**：重叠计算和通信（第6章），使用高效注意力（Flash Attention，第16章），优化数据加载（防止GPU空闲），减少检查点开销（异步检查点、将检查点复制到快速NVMe存储，然后后台复制到持久化存储）。

- **Build vs buy**: 在小规模（约 6+ 个月的持续使用，<256 GPUs), cloud is cheaper (no upfront cost, pay per hour). At large scale (>1000 GPUs），拥有硬件成本更低（~2-3 倍的总拥有成本（TCO）在 3 年内）。大多数 AI 公司采用混合策略：用于长期训练的自有集群和用于突发容量和实验的云服务。

## 数据库扩展

- **读副本**：将读查询路由到主数据库的副本。主数据库处理写操作，副本处理读操作。由于大多数工作负载是读取密集型（高达95%的读取），这会以线性比例提高读取吞吐量。

- 分区（分片，来自文件 01）：将数据分布在多个数据库中。每个分区是独立的，支持并行读写。挑战在于跨分区查询（从不同分片获取数据）。

- **连接池**：数据库有有限的连接容量。连接池（如PostgreSQL中的PgBouncer）在请求之间重用连接，防止当数百个服务实例每个都尝试连接时出现连接耗尽的情况。

## 搜索与向量系统

### 文本搜索

- **倒排索引**：文本搜索的基础。为每个单词存储包含该单词的文档列表。查询与每个查询词的列表相交。Elasticsearch是标准：分布式、实时支持全文搜索、聚合和地理空间查询。

- **BM25**: 一种标准的文本检索评分函数。它根据词频、逆文档频率和文档长度进行评分。简单但有效，仍然与神经方法在关键词密集查询中竞争良好。

### 向量搜索

- **向量数据库**存储嵌入（高维向量）并支持快速近似邻搜索（ANN）。给定查询嵌入，找到与存储嵌入最相似的 $k$ 个。

- **FAISS**（Facebook AI Similarity Search）：一个用于ANN搜索的库（不是数据库），支持多种索引类型：
    - **Flat**：精确搜索， $O(n)$用于小数据集或作为基准数据。
    - IVF（倒排文件）：将向量分区为簇，仅搜索最近的簇。 $O(n/k)$ 对于每个查询：
    - **HNSW**（层次化可导航小世界）：基于图的。构建层次化图，从粗到细导航。速度极快且准确，是大多数应用的默认选择。
    - **产品量化（PQ）**：将向量压缩成紧凑代码以实现内存高效搜索。牺牲精度换取内存。

- **管理向量数据库**：Pinecone、Weaviate、Milvus、Qdrant。它们能够处理FAISS无法实现的缩放、复制和实时更新功能。

- **对于RAG（检索增强生成）**：用户查询 → 使用文本编码器进行嵌入 → 在向量数据库中搜索与相关文档相关的文档 → 将检索到的文档prepend到LLM提示中。检索的质量直接影响LLM响应的质量。

## 可观察性

- **可观察性** 是从系统外部输出中理解其内部状态的能力。三个支柱：

### 日志记录

- **结构化日志**（JSON）是可搜索和解析的。未结构化的日志（例如“ERROR: something failed”）不是。始终记录：时间戳、服务名称、请求ID（用于跨服务跟踪）、严重性和相关的上下文。

- **ELK stack** (Elasticsearch, logstash, Kibana): 一个标准的日志管道。logstash收集和转换日志，elasticsearch索引它们，kibana可视化和搜索它们。

### 指标

- **指标**是随着时间变化的数值测量：请求率、错误率、延迟百分位数、GPU利用率、队列深度。**Prometheus**从服务中抓取指标；**Grafana**在仪表板中可视化它们，并带有警报功能。

- **RED方法**用于服务：**R**ate（每秒请求数）、**E**rrors（错误率）、**D**uration（延迟）。为每个服务监控这些指标。

- **资源的USE方法**：利用率（%在用）、饱和度（队列深度）、错误。监控每个资源（CPU、GPU、内存、硬盘、网络）。

### 跟踪

- **分布式跟踪**遵循单个请求在多个服务之间传播。用户请求到达API网关 → 特性服务 → 模型服务 → 后处理。一个**跟踪**记录每个跳过的 timing，显示延迟花费在哪里。

- **OpenTelemetry**：分布式追踪、指标和日志的标准。在代码中只进行一次仪器化，导出到任何后端（Jaeger、Zipkin、Datadog）。

## 可靠性

- **SLO**（服务级别目标）：目标可靠度。例如，“99.9%的请求在200毫秒内完成。”这给出了一个具体的错误预算：大约43分钟每月可以慢或失败。

- **SLI**（服务级别指示器）：测量。"过去5分钟内99百分位的延迟。"

- **SLA**（服务级别协议）：合同承诺，带有后果。"如果可用性低于99.95%，客户将获得信用。"

- **错误预算**：如果你的SLO是99.9%，而你目前处于99.99%，那么你就有了处理风险变化（部署新模型、迁移数据库）的预算。如果你目前处于99.85%，则需要冻结所有更改，专注于可靠性。错误预算将可靠性从一个抽象目标变成了可衡量的资源。

- **混沌工程**：故意引入故障（杀死服务器、增加网络延迟、损坏数据）来测试系统是否正确处理这些故障。Netflix的混沌猴子随机终止生产实例。如果系统仍然运行，说明系统具有弹性。如果系统崩溃，你在此之前就发现了问题，而不是在用户面前崩溃。

## CI/CD

持续集成（CI）和持续部署（CD）是软件开发中用于自动化测试、构建和部署的流程。CI流程通常包括以下步骤：

1. **代码提交**：开发者将代码提交到版本控制系统（如Git）。
2. **触发构建**：版本控制系统检测到代码提交后，自动触发构建过程。
3. **自动化测试**：构建过程中运行一系列自动化测试，确保代码质量。
4. **构建成功**：如果所有测试通过，构建过程继续进行。

CD流程通常包括以下步骤：

1. **构建成功**：CI流程完成后，构建成功的代码被部署到测试环境或预生产环境中。
2. **自动化测试**：在测试环境中运行一系列自动化测试，确保代码质量。
3. **部署成功**：如果所有测试通过，代码被部署到生产环境中。

通过这种方式，CI/CD流程可以显著提高软件开发的效率和稳定性。

- **持续集成**：自动构建和测试每次代码更改。每次推送都会触发：lint、类型检查、单元测试、集成测试。如果任何失败，更改会被拒绝。这可以在问题进入生产之前捕获到错误。

- **持续部署**：自动部署通过CI验证的更改。部署策略：

    - **蓝绿**：运行两个完全相同的环境（蓝色是当前，绿色是新）。立即切换流量从蓝色到绿色。如果绿色失败，则立即回滚到蓝色（即时回滚）。

    - **Canary**: 将一小部分流量（1-5%）路由到新版本。监控错误情况。如果指标看起来良好，逐渐增加流量。这限制了部署失败的影响范围。

    - **Feature flags**: 部署新的代码但隐藏在标志后面。将标志启用给内部测试者、然后beta用户，最后对所有人开放。将部署（代码上线）与发布（用户看到功能）分开。

- 对于 ML：CI/CD 包含模型特定步骤。模型更改触发：形状测试、梯度检查、在未分发集上评估（准确性不得下降）、阴影部署（运行新模型与旧模型并比较输出）和渐进式发布（从 1% → 100%）。
