# 大规模基础设施

*为数百万用户提供服务需要的不只是一台服务器。本篇涵盖可扩展性模式、分布式系统基础、微服务、数据管道、数据库扩展、搜索与向量系统、可观测性、可靠性工程以及 CI/CD。*

- 每秒服务 1 个请求的模型可以运行在笔记本电脑上；要以 99.9% 的可用性每秒服务 100,000 个请求，则需要分布式系统、自动故障转移和精心设计的数据管道。本篇介绍连接这两个规模的系统模式。

## 可扩展性

- **垂直扩展（scale up）**：换一台更大的机器，增加 CPU、RAM 或更大的 GPU。它简单，但有硬上限（可获得的最大机器），并且存在单点故障。

- **水平扩展（scale out）**：增加更多机器，每台机器处理一部分流量。它没有单机上限，但需要负载均衡（第 01 篇）、数据分区以及分布式状态处理。

- **无状态服务**默认就容易水平扩展。在负载均衡器后增加更多实例即可。启动时加载权重、独立处理请求的模型推理服务器就是无状态的——任意实例都可以处理任意请求。

- **有状态服务**（数据库、KV cache、特征存储）更难扩展。状态必须在机器之间分区（分片，第 01 篇），并进行复制以容忍故障。

- **可扩展性方程**：对于有 $n$ 台服务器的系统：
    - **理想情况**：吞吐量线性扩展（$n$ 台服务器 → $n\times$ 吞吐量）。
    - **实际情况**：协调、负载均衡和数据传输的开销会让吞吐量次线性扩展。Amdahl 定律（第 13 章）同样适用：串行部分（共享状态、协调）会限制加速比。

## 分布式系统

- **分布式系统**是一组相互协调以提供服务的机器。它面临的基本挑战包括：

- **网络分区**：机器并不总能互相通信。网线可能被切断，交换机可能故障，数据中心可能断电。系统必须处理部分故障。

- **时钟偏差**：不同机器的时钟可能不同。“机器 1 上的事件 A 发生于 10:00:01”和“机器 2 上的事件 B 发生于 10:00:01”并不意味着两者同时发生。**逻辑时钟**（Lamport 时间戳、向量时钟）不依赖物理时钟也能建立顺序。

- **共识**：多台机器如何就一个值达成一致（例如谁是 leader）？**Raft** 是标准共识算法。节点集群选出一个 leader，由 leader 处理所有写入。如果 leader 故障，剩余节点会选出新的 leader。系统需要多数节点（5 个节点中至少 3 个）才能运行，因此可以容忍 $\lfloor(n-1)/2\rfloor$ 个故障。

- **分布式锁**确保只有一台机器执行关键操作。**Redlock**（基于 Redis）会在多个 Redis 实例上获取锁；如果多数实例授予锁，就算获取成功。它可用于防止重复部署模型，或确保只有一个训练任务写入 checkpoint。

## 微服务

![微服务机器学习架构：API 网关把请求路由到特征、模型和日志服务，每个服务拥有自己的数据库，并通过消息队列连接](../images/microservices_architecture.svg)

- **微服务**把系统拆分成小型、可独立部署的服务，每个服务负责一个领域：

```
┌─────────────┐  ┌──────────────┐  ┌─────────────┐
│ API Gateway │→ │ Feature Svc  │→ │ Feature DB  │
└─────────────┘  └──────────────┘  └─────────────┘
       │
       ├────────→ ┌──────────────┐  ┌─────────────┐
       │          │ Model Svc    │→ │ Model Store │
       │          └──────────────┘  └─────────────┘
       │
       └────────→ ┌──────────────┐  ┌─────────────┐
                  │ Logging Svc  │→ │ Log Store   │
                  └──────────────┘  └─────────────┘
```

- **优势**：可以独立部署（更新 model service 而不触碰 feature service）；可以独立扩展（按请求负载扩展模型服务器，按特征存储读取速率扩展特征服务器）；技术自由（model service 用 Python，feature service 用 Go）。

- **缺点**：网络开销（每次服务调用都需要一次网络往返）；复杂性（调试会跨越多个服务）；数据一致性（无法进行跨服务事务）。

- **服务发现**：API 网关如何找到 model service？选项包括基于 DNS（每个服务注册一个 DNS 名称）、K8s service（内置）或服务注册中心（Consul、Eureka）。

- **Saga 模式**：对于跨越多个服务的操作（创建用户 + 分配资源 + 发送欢迎邮件），使用 saga：把操作拆成一系列本地事务，并在某一步失败时执行补偿操作。

## 数据管道

- 机器学习系统消耗海量数据。**数据管道**负责移动、转换并提供这些数据：

### 批处理

- 按固定间隔（每小时、每天）处理大量数据。

- **MapReduce**：最初的批处理范式。Map（独立转换每条记录）→ Shuffle（按 key 分组）→ Reduce（聚合每组）。概念简单，但实现起来较为繁琐。

- **Apache Spark**：现代批处理引擎。它使用内存处理（对于迭代算法，比 MapReduce 快 100 倍），支持 SQL、DataFrame 和机器学习管道，是大规模特征工程的标准工具。

- **示例**：为推荐系统计算用户特征。输入是最近 30 天的 1B 条用户活动事件，输出是 100M 个用户特征向量。每天运行一个 Spark 任务，并将结果写入特征存储。

### 流处理

- 数据到达时实时处理数据（亚秒级延迟）。

- **Apache Flink**：领先的流处理引擎。它支持 exactly-once 处理、事件时间处理（按照事件发生时间而不是到达时间处理）、窗口（滚动窗口、滑动窗口、会话窗口）。

- **Kafka Streams**：Kafka 内置的轻量流处理工具。它适合执行过滤、聚合等简单转换，无需部署独立集群。

- **示例**：实时欺诈检测。每笔信用卡交易都是一个 Kafka 事件；Flink 任务计算运行统计量（交易频率、位置变化），并在 100ms 内标记异常。

### Lambda 架构

- 组合批处理与流处理。**批处理层**提供准确、全面的结果（但有延迟）；**速度层**提供近似的实时结果；**服务层**合并两者。

- 实践中，许多团队现在使用 **Kappa 架构**：只做流处理，把数据流作为事实来源。数据流可重放（Kafka 会保留事件），因此可以通过重放数据流来模拟批处理。

## 机器学习训练基础设施

- 训练一个前沿模型（100B 以上参数）是一个大规模基础设施问题：数千个 GPU 运行数月，消耗兆瓦级电力，产生 PB 级数据，成本达数千万美元。基础设施决定训练是成功还是失败。

### GPU 集群

- 训练集群是由高速网络连接起来的一组 GPU 服务器。关键组件包括：

![GPU 集群：每个节点有 8 个通过 NVLink 连接的 GPU，节点通过 InfiniBand 以 fat tree 拓扑连接，可从 64 个 GPU 扩展到 16,000 个以上](../images/gpu_cluster_topology.svg)

- **GPU 服务器（节点）**：每台服务器有 4–8 个 GPU。典型配置为：8 × H100 GPU、2 × AMD EPYC CPU、2 TB RAM、30 TB NVMe SSD。同一节点内的 GPU 通过 **NVLink** 连接（H100 上每个 GPU 为 900 GB/s），速度是 PCIe 的 30 倍。

- **集群规模**：小型训练集群有 64–256 个 GPU（8–32 个节点）；前沿模型训练集群有 4,000–32,000 个 GPU（500–4000 个节点）。Meta 的 Llama 3 使用了 16,384 个 H100 GPU；Google 在拥有 8,000 个以上芯片的 TPU pod 上训练。

- **粗略估算**：训练 70B 模型需要约 $2M 的计算成本；训练 400B 以上的前沿模型需要约 $50–100M。集群硬件本身按 H100 价格约需 $500M–$1B（每个 GPU $30K × 16,000 个 GPU = $480M）。

### 网络拓扑

- GPU 节点之间的网络是最关键的基础设施组件。如果 GPU 不能足够快地交换梯度，它们就会闲置，等待通信完成。

- **InfiniBand** 是 GPU 集群网络的标准。NVIDIA 的 **Quantum-2 InfiniBand** 每个端口提供 400 Gb/s。每个节点通常有 8 个 InfiniBand 端口（每个 GPU 一个），因此节点总二分带宽为 400 GB/s。

- **RDMA（Remote Direct Memory Access，远程直接内存访问）**：InfiniBand 支持 RDMA，可以直接在不同节点的 GPU 内存之间传输数据，而不经过 CPU。这会把延迟从约 100μs（TCP）降到约 1μs，是高效梯度 all-reduce（第 6 章）的必要条件。

- **网络拓扑很重要**：**fat tree**（Clos 网络）提供完整二分带宽（任意 GPU 都能以全速与任意其他 GPU 通信）。更便宜的拓扑（**rail-optimised**、**3D torus**）带宽更低但成本更小。拓扑必须与并行策略匹配：
    - **数据并行**：在所有 GPU 之间 all-reduce → 需要高二分带宽（fat tree）。
    - **张量并行**：节点内部通信 → 由 NVLink 处理（不需要网络）。
    - **流水线并行**：相邻流水线阶段之间通信 → 只需要特定节点对之间有带宽（rail-optimised 就足够）。

- **以太网替代方案**：**RoCE v2**（融合以太网上的 RDMA）在标准以太网基础设施上提供 RDMA。它比 InfiniBand 便宜，但延迟更高、拥塞更多。Google 的部分 TPU pod 网络使用 RoCE。Ultra Ethernet Consortium 正在为 AI 工作负载开发无损以太网。

### 训练存储

- 训练需要三个存储层级：

    - **数据集存储**：训练语料（1–100 TB 文本，或 PB 级多模态数据）。它存储在分布式文件系统或对象存储中，必须支持高吞吐顺序读取（data loader 会以大 batch 读取数据）。常见 HPC 文件系统有 **Lustre** 和 **GPFS**；云端替代方案包括 **FSx for Lustre**（AWS）和 **Filestore**（GCP）。

    - **Checkpoint 存储**：定期保存训练状态（模型权重 + 优化器状态 + scheduler 状态）。对于使用混合精度和 Adam 优化器的 70B 模型，每个 checkpoint 约 560 GB（70B × 4 bytes × 2 份优化器状态）。运行 3 个月、每小时保存一次会得到约 2000 个 checkpoint，即 1.1 PB。实践中只保留最新的 N 个 checkpoint，并删除旧的。保存速度必须足够快，以免显著拖慢训练。

    - **日志与指标**：实验跟踪数据（损失曲线、学习率计划、梯度范数）。数据量相对小，但必须实时写入。W&B、MLflow 或 TensorBoard 可以处理这类数据。

- **存储瓶颈**：一个 16,000 GPU 集群加载训练 batch 时，需要持续读取约 100 GB/s 的数据。如果文件系统无法维持这一吞吐量，GPU 就会闲置等待数据。数据管道优化（预取、缓存、使用 WebDataset 或 Mosaic Streaming 的格式优化）至关重要。

### 作业调度

- GPU 集群为多个团队和项目服务。**作业调度器**负责把 GPU 分配给训练作业：

- **SLURM**：标准 HPC 作业调度器。用户提交作业时指定 GPU 数量、内存和时间限制；SLURM 分配资源并管理队列，支持按优先级调度、抢占和团队间公平共享。

- **使用 GPU 调度的 Kubernetes**（第 18 章第 02 篇）：云原生方案。K8s GPU device plugin 把 GPU 暴露为可调度资源。**Volcano** 和 **Run:ai** 增加面向机器学习的调度功能：gang scheduling（一次为作业分配全部 GPU，而非逐个分配）、优先级队列和 GPU 时间共享。

- **调度挑战**：
    - **碎片化**：一个有 1000 个 GPU 的集群可能有 200 个空闲 GPU，但分散在 50 个节点上（每个节点空闲 4 个）。需要连续 128 个 GPU 的任务无法运行，尽管空闲 GPU 总数足够。**碎片整理**（迁移作业以集中空闲 GPU）或**拓扑感知调度**（分配连接良好的 GPU）可以解决问题。
    - **优先级与抢占**：紧急实验应该抢占低优先级作业，但抢占一个已经运行 2 天的训练任务会浪费计算。调度器必须在优先级和效率之间平衡。
    - **公平共享**：即使某个团队提交的任务超过其份额，各团队长期仍应获得分配给自己的计算资源比例。

### 容错

- 在数千个 GPU 运行数月的规模上，硬件故障不是例外，而是日常事件。16,000 GPU 集群的平均故障间隔时间以小时计，而不是以月计。

- **常见故障**：GPU 内存错误（可由 ECC 更正和不可更正）、NVLink 故障（节点内 GPU 到 GPU 的通信）、InfiniBand 链路故障（节点间通信）、节点崩溃（kernel panic、PSU 故障）以及存储故障（磁盘或控制器故障）。

- **Checkpoint** 是主要防线。每 N 步保存完整训练状态（模型、优化器、data loader 位置）。发生故障时，识别故障节点，替换或移除该节点，再从最新 checkpoint 重启训练。一次故障的代价，就是上一次 checkpoint 之后到故障发生之间的计算。

- **Checkpoint 频率的折中**：频繁保存（每 10 分钟）在故障时浪费的计算更少，但会拖慢训练（保存 560 GB 需要时间）；不频繁保存（每 2 小时）速度更快，但故障时最多浪费 2 小时计算。大多数团队每 20–60 分钟保存一次。

- **弹性训练**：现代框架（PyTorch Elastic、DeepSpeed）支持在不重启的情况下调整训练规模。如果 500 个节点中有 2 个故障，训练可以继续使用 498 个节点；故障节点更换后重新上线，训练会自动将它们纳入。

- **健康监控**：持续监控所有 GPU（温度、内存错误、计算吞吐量）、网络链路（丢包、延迟）和存储（吞吐量、错误率），并对异常自动告警。一些集群会定期执行 GPU 健康检查（短计算测试），在硬件故障前主动发现正在退化的设备。

- **实际规模**：训练 Meta 的 Llama 3（16,384 个 H100，54 天）经历了约 466 次作业中断。有效训练时间只有墙钟时间的约 90%，10% 损失在故障与恢复上。能把有效率做到 90%（而不是 50% 或 70%）的基础设施，正是能训练前沿模型的组织与其他组织之间的差别。

### 成本与效率

- 训练基础设施成本主要由 GPU 小时构成：

| 组件 | 总成本占比 |
|-----------|----------------|
| GPU 计算 | 70–80% |
| 网络（InfiniBand） | 10–15% |
| 存储 | 5–10% |
| 散热与电力 | 5–10% |

- **GPU 利用率**（Model FLOPs Utilisation，MFU）衡量 GPU 理论峰值性能中实际用于有效计算的比例。H100 的峰值为 989 TFLOPS（FP8）。MFU 达到 40–50% 就很好，50–60% 则非常优秀。差距来自通信开销（all-reduce、流水线气泡）、内存带宽限制，以及 checkpoint 和数据加载期间的空闲时间。

- **提高 MFU**：重叠计算与通信（第 6 章）；使用高效 attention（Flash Attention，第 16 章）；优化数据加载（避免 GPU 饥饿）；减少 checkpoint 开销（异步 checkpoint，先保存到快速 NVMe，再在后台复制到持久存储）。

- **自建还是购买**：在小规模（少于 256 个 GPU）下，云服务更便宜（无前期成本，按小时付费）；在大规模（超过 1000 个 GPU，持续使用 6 个月以上）下，自有硬件更便宜（3 年总拥有成本约低 2–3 倍）。多数 AI 公司采用混合方式：用自有集群做持续训练，用云服务应对突发容量和实验。

## 数据库扩展

- **读副本**：把读查询路由到主数据库的副本。主库处理写入，副本处理读取。由于大多数工作负载以读取为主（读取占 95% 以上），随着副本数量增加，读取吞吐量可以线性扩展。

- **分区**（分片，第 01 篇）：把数据拆分到多个数据库中。每个分区独立运行，可以并行读写；挑战在于跨分区查询（从不同分片连接数据）。

- **连接池**：数据库的连接容量有限。连接池（PostgreSQL 的 PgBouncer）会在请求之间复用连接，防止数百个服务实例各自尝试连接而耗尽连接。

## 搜索与向量系统

### 文本搜索

- **倒排索引**：文本搜索的基础。对每个单词保存包含该词的文档列表；查询时求各个查询词对应列表的交集。**Elasticsearch** 是标准工具：分布式、实时，支持全文搜索、聚合和地理空间查询。

- **BM25**：标准文本检索评分函数。它依据词频、逆文档频率和文档长度归一化为文档打分。它简单有效，在关键词较多的查询上仍能与神经方法竞争。

### 向量搜索

- **向量数据库**存储 embedding（高维向量），并支持快速的**近似最近邻（approximate nearest neighbour，ANN）**搜索。给定查询 embedding，找到最相似的 $k$ 个已存储 embedding。

- **FAISS**（Facebook AI Similarity Search）是用于 ANN 搜索的库（不是数据库），支持多种索引类型：
    - **Flat**：精确搜索，$O(n)$。用于小数据集或作为 ground truth。
    - **IVF（倒排文件）**：把向量分成多个簇，只搜索最近的簇。每次查询为 $O(n/k)$。
    - **HNSW（Hierarchical Navigable Small World）**：基于图。构建层级图，从粗到细导航。速度和准确率都很高，是大多数应用的默认选择。
    - **乘积量化（Product Quantisation，PQ）**：把向量压缩为紧凑编码，以节省搜索内存；代价是准确率下降。

- **托管向量数据库**：Pinecone、Weaviate、Milvus、Qdrant。它们处理扩展、复制和实时更新，而 FAISS 不负责这些。

- **对于 RAG**（Retrieval-Augmented Generation，检索增强生成）：用户查询 → 使用文本 encoder 生成 embedding → 在向量数据库中搜索相关文档 → 将检索到的文档前置到 LLM prompt。检索质量会直接决定 LLM 响应的质量。

## 可观测性

- **可观测性**是通过系统的外部输出理解系统内部发生了什么的能力。它有三大支柱：

### 日志

- **结构化日志**（JSON）可搜索、可解析；非结构化日志（“ERROR: something failed”）则不行。始终记录：时间戳、服务名、请求 ID（用于跨服务追踪）、严重级别以及相关上下文。

- **ELK 栈**（Elasticsearch、Logstash、Kibana）是标准日志管道。Logstash 收集并转换日志，Elasticsearch 为日志建立索引，Kibana 对日志进行可视化和搜索。

### 指标

- **指标**是随时间变化的数值测量：请求速率、错误率、延迟百分位、GPU 利用率、队列深度。**Prometheus** 从服务抓取指标；**Grafana** 在带告警的仪表盘中将其可视化。

- 服务使用 **RED 方法**：**R**ate（请求/秒）、**E**rrors（错误率）、**D**uration（延迟）。每个服务都要监控这些指标。

- 资源使用 **USE 方法**：**U**tilisation（利用率，使用百分比）、**S**aturation（饱和度，队列深度）、**E**rrors（错误）。每项资源（CPU、GPU、内存、磁盘、网络）都要监控这些指标。

### 追踪

- **分布式追踪**跟踪一条请求经过多个服务的全过程。用户请求会经过 API 网关 → 特征服务 → 模型服务 → 后处理。一个**trace**记录每一跳的耗时，显示延迟花在了哪里。

- **OpenTelemetry**：用于 trace、指标和日志的开放标准。只需对代码进行一次插桩，就可以导出到任意后端（Jaeger、Zipkin、Datadog）。

## 可靠性

- **SLO（Service Level Objective，服务等级目标）**：目标可靠性，例如“99.9% 的请求在 <200ms 内完成”。这给出了具体的错误预算：每月约 43 分钟的请求（0.1%）可以变慢或失败。

- **SLI（Service Level Indicator，服务等级指标）**：实际测量值，例如“最近 5 分钟的第 99 百分位延迟”。

- **SLA（Service Level Agreement，服务等级协议）**：带有后果的合同承诺，例如“如果可用性降到 99.95% 以下，客户将获得额度补偿”。

- **错误预算**：如果 SLO 是 99.9%，而当前达到 99.99%，就有预算进行有风险的变更（部署新模型、迁移数据库）；如果当前只有 99.85%，就应冻结所有变更，把重点放在可靠性上。错误预算把抽象的可靠性目标变成可度量的资源。

- **混沌工程**：主动注入故障（终止服务器、增加网络延迟、破坏数据），测试系统能否正确处理。Netflix 的 Chaos Monkey 会随机终止生产实例。如果系统仍能运行，说明它有韧性；如果系统崩溃，就在用户发现问题之前找到了 bug。

## CI/CD

- **持续集成（Continuous Integration）**：自动构建并测试每次代码变更。每次 push 都触发 lint、类型检查、单元测试和集成测试；任何一项失败，变更都会被拒绝。这能在 bug 进入生产环境之前发现它。

- **持续部署（Continuous Deployment）**：自动部署通过 CI 的变更。部署策略包括：

    - **蓝绿部署**：运行两个相同环境（blue = 当前环境，green = 新环境），瞬间将流量从 blue 切换到 green。如果 green 失败，就切回 blue（立即回滚）。

    - **金丝雀发布**：把一小部分流量（1–5%）路由到新版本，监控错误；如果指标良好，就逐步增加流量。这限制了坏部署的影响范围。

    - **功能开关**：部署新代码，但把它隐藏在开关后面。先为一部分用户（内部测试者，再到 beta 用户，最后所有用户）启用开关。这样就把部署（代码已上线）与发布（用户能看到功能）解耦。

- 对机器学习而言，CI/CD 还包括模型专属步骤。模型变更会触发：单元测试（形状测试、梯度检查）、留出集评估（准确率不能退化）、影子部署（让新旧模型并行运行并比较输出），以及渐进式发布（从 1% canary 逐步到 100%）。
