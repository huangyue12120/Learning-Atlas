# 主管 / 编排器—工作者模式

> 一名主导智能体负责规划和委派；专业工作者在并行上下文中执行并报告。这是 Anthropic Research 系统背后的模式（Claude Opus 4 作为主导，Sonnet 4 作为子智能体），在内部研究评估中比单智能体 Opus 4 高出 90.2%。Anthropic 的工程文章报告，BrowseComp 上 80% 的方差仅由 token 使用量解释——多智能体的主要优势，是每个子智能体都获得新的上下文窗口。本课从原语构建主管模式，并涵盖 2026 年生产部署得出的工程经验。

**类型：** 学习 + 构建
**语言：** Python（标准库，`threading`）
**前置要求：** 第 16 阶段 · 04（原语模型）
**用时：** 约 75 分钟

## 问题

研究是单智能体系统最典型的失败任务。你问“2023 到 2026 年，多智能体系统发生了什么变化？”单个智能体依次读五篇论文，半个上下文被论文文本填满，之后还得同时推理它们。读到第五篇时，它已忘了第一篇，也无法并行。

主管模式解决这个问题：一名主导智能体规划检索，将每个子问题交给工作者，再进行综合。每个工作者都为一个狭窄问题获得自己的 200k-token 窗口。主导者从不阅读原始论文——只看工作者摘要。

Anthropic 的生产 Research 系统报告，相较单个 Opus 4，内部研究评估提升 90.2%。同一文章指出，BrowseComp 方差的 80% 仅由*token 使用量*解释。每个子智能体获得的新上下文是主要机制。

## 概念

### 模式形状

```
                 ┌──────────────┐
                 │   主导者      │  规划、分解、
                 │  (Opus 4)    │  综合
                 └──┬────┬───┬──┘
                    │    │   │
            ┌───────┘    │   └───────┐
            ▼            ▼           ▼
      ┌─────────┐  ┌─────────┐  ┌─────────┐
      │ 工作者 1 │  │ 工作者 2 │  │ 工作者 3 │
      │(Sonnet) │  │(Sonnet) │  │(Sonnet) │
      └─────────┘  └─────────┘  └─────────┘
        新鲜          新鲜         新鲜
        上下文        上下文       上下文
```

主导者从不读原始材料。工作者在主导者综合前也看不到彼此的工作。每一条箭头都是带有狭窄制品的交接。

### 为什么会赢

有三个机制：

1. **每个子智能体的新上下文。** 探索“FIPA-ACL 传承”的工作者不会带上主导者规划时花费的 40k token；它为一个问题获得 200k 窗口。
2. **通过提示词专业化。** 主导者的提示词是“分解和综合”，而非“研究”。每个工作者的提示词很窄：“找出 X 发生了什么变化。”聚焦的提示词产生聚焦的输出。
3. **并行。** 工作者并发运行。墙钟时间大约为 `max(worker_times) + plan + synthesis`，而非 `sum(worker_times)`。

### 工程经验（Anthropic 2025）

Anthropic 文章列出了在 2026 年仍有意义的几条生产经验：

- **让投入与查询复杂度匹配。** 简单查询：一个智能体，3–10 次工具调用。复杂查询：10 个以上智能体。应由主导者估计，而非调用者。
- **先宽后窄。** 先分解为宽泛的子问题，再根据答案是否需要深度，为每个子问题派生更多工作者。
- **彩虹部署。** 智能体是长时间运行且有状态的。传统蓝绿部署不适用。Anthropic 使用彩虹部署：新版本逐渐上线，同时旧版本逐渐排空。
- **token 使用占主导。** 多智能体消耗的 token 约为单智能体的 15 倍。只有当任务价值足以证明成本合理时才运行它。

### 图原生的转向

LangGraph 最初发布过带高级 `create_supervisor` 辅助器的 `langgraph-supervisor` 库。2025 年，LangChain 将推荐方式改为通过工具调用直接实现主管模式，因为工具调用能更精确地控制*主管看见什么*（上下文工程）。该库仍可使用；文档如今推荐工具调用形式。

### 失效模式

- **主导者虚构规划。** 若主导者生成的子问题没有真正分解原问题，工作者会对错误目标做精确研究。
- **工作者过度探索。** 若没有明确范围边界，工作者会漂移到分配子问题之外，污染综合步骤。
- **综合冲突。** 两个工作者返回相互矛盾的事实。主导者必须重问（增加一轮）或明确指出分歧。悄悄选一边是最糟糕的失败：用户永远不知道存在分歧。

### 主管模式何时不对

- **顺序任务。** 若第 2 步确实依赖第 1 步的输出，并行没有收益。使用流水线（CrewAI Sequential、LangGraph 线性图）。
- **简单查询。** 单智能体更快也更便宜。在派生工作者前使用主导者的“投入缩放”检查。
- **严格确定性。** 主管模式使用 LLM 选择的委派。当审计/回放比适应性更重要时，静态图更好。

## 动手构建

`code/main.py` 使用 `threading` 实现由三名并行工作者组成的主管。主导者将查询分解为子问题，工作者并发运行每个子问题，主导者再综合。没有真实 LLM——工作者以脚本方式模拟获取与摘要。

关键结构：

- `Lead.plan(query)` 将查询拆成 3 个子问题。
- `Worker.run(sub_q)` 返回伪摘要（生产中可以是任意使用工具的智能体）。
- `Lead.run(query)` 在线程中启动工作者、等待汇合并综合。

运行：

```
python3 code/main.py
```

输出展示规划、带有开始/结束时间戳的并行工作者跟踪，以及最终综合。墙钟时间显示出优势：三个各需 0.3 秒的工作者在约 0.35 秒内运行完毕，而不是 0.9 秒。

## 实际使用

`outputs/skill-supervisor-designer.md` 接收用户查询并生成主管模式设计：主导者系统提示词、工作者角色、子问题分解规则与综合模板。构建新的研究型智能体系统前使用它。

## 交付物

部署主管模式前的检查表：

- **模型配对。** 主导者使用推理级模型（Opus 级、`o3` 级）；工作者使用更快、更便宜的模型（Sonnet、`o4-mini`）。
- **工作者超时。** 任何超过中位运行时间 2 倍的工作者都会被终止；主导者要么用更窄范围重派，要么在没有它的情况下继续。
- **每工作者 token 上限。** 设置硬限制（例如预期综合输入的 10 倍），避免失控工作者耗尽预算。
- **可观测性。** 追踪主导者规划、每个工作者的工具调用和综合，为事后调试提供基础。
- **彩虹上线。** 有状态的长时间运行智能体需要渐进版本迁移，而非热切换。

## 练习

1. 运行 `code/main.py`，再将主导者改为派生 5 名工作者而非 3 名。观察墙钟效应。在本演示中，工作者数量到多少时，派生开销超过并行节省？
2. 实现工作者超时：终止运行超过 0.5 秒的工作者，让主导者综合其余结果。你需要哪些可观测性来知道某个工作者被截断？
3. 向主导者的综合加入冲突检测步骤：若两个工作者返回矛盾回答，主导者标明分歧，而非选一边。不调用 LLM 时如何检测矛盾？
4. 阅读 Anthropic 的 Research 系统工程文章。列出这个玩具演示若要在生产运行必须采用的三项做法。
5. 比较 LangGraph 的 `create_supervisor`（旧版）和新的工具调用建议。哪一个对主管所见信息的控制更好？为何 Anthropic 明确只将子答案而非原始工作者上下文传入综合？

## 关键术语

| 术语 | 常见说法 | 实际含义 |
|---|---|---|
| 主管 | “主导智能体” | 负责规划、委派和综合的编排智能体；本身不做具体工作。 |
| 工作者 | “子智能体” | 由主管在狭窄范围内调用、且拥有自己上下文窗口的聚焦智能体。 |
| 编排器—工作者 | “主管模式” | 同一事物的不同名称；2026 年文献两者都用。 |
| 新鲜上下文 | “干净窗口” | 工作者的上下文从系统提示词和分配问题开始，而非主导者历史。 |
| 彩虹部署 | “渐进上线” | 长时间运行的有状态智能体需要有版本的排空—替换，而非蓝绿。 |
| token 占主导 | “上下文是变量” | Anthropic 指出，研究评估方差的 80% 来自总 token 使用量，而非模型选择。 |
| 投入缩放 | “让智能体数匹配复杂度” | 主导者估计查询难度，并据此派生 1 个或 10 个以上工作者。 |
| 综合冲突 | “工作者意见不一” | 两个工作者返回矛盾事实；主导者必须暴露分歧，而不能静默选择。 |
