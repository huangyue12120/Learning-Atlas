# 共享记忆与黑板模式

> 2026 年多智能体系统中并存两种做法：**消息池**（每个人都能看到每个人的消息，如 AutoGen GroupChat 或 MetaGPT）和**带订阅的黑板**（智能体订阅相关事件，如 Context-Aware MCP 或 Matrix 框架）。两者都是多智能体系统中唯一有状态的部分——因此有趣的 bug 也都出现在这里。典型失效模式是**记忆投毒**：一个智能体幻觉出一条“事实”，其他智能体将其当作已验证内容，准确率以比立即崩溃更难调试的方式逐渐衰退。本课用标准库构建两种结构、注入投毒攻击，并展示生产中真正有效的三种缓解措施。

**类型：** 学习 + 构建
**语言：** Python（标准库，`threading`）
**前置要求：** 第 16 阶段 · 04（原语模型），第 16 阶段 · 09（并行群体网络）
**用时：** 约 75 分钟

## 问题

多智能体系统需要一个让智能体共享事实的地方。字面做法是“把所有内容放在消息中传递”——但那是在用额外复制重新发明共享状态。另一种是“给每个人一个全局日志”——但全局日志无限增长且容易投毒。第三种是“按智能体投影视图”——可扩展但模式负担重。

当某个智能体产生幻觉并把它写入共享状态时，读取状态的所有下游智能体都会将幻觉当作事实。等人类发现时，推理链已经有五步深，根因是写下的第三条消息。调试多智能体准确率衰退比调试崩溃更困难。

这种失效模式称为记忆投毒。它是 MAST 分类法中记录第二多的失效家族（Cemri 等人，arXiv:2503.13657），而且是结构性的：任何没有来源信息和不可写验证者的共享记忆设计最终都会出现它。

## 概念

### 两种主要拓扑

**完整消息池。** 每个智能体读取每条消息。AutoGen GroupChat 与 MetaGPT 使用此模式。它简单、透明、可检查，但无法扩展超过约 10 个智能体，因为每个智能体的上下文都会被其他人的工作填满。

```
智能体 A ──写入──▶ ┌────────────────┐ ◀──读取── 智能体 D
                    │    消息池       │
智能体 B ──写入──▶ │                │ ◀──读取── 智能体 E
                    │   （全局日志）  │
智能体 C ──写入──▶ └────────────────┘ ◀──读取── 智能体 F
```

**带订阅的黑板。** 智能体声明对主题的兴趣；底层只路由相关消息。CA-MCP（arXiv:2601.11595）和 Matrix 去中心化框架（arXiv:2511.21686）使用此模式。它可扩展得更远，但需要事先设计模式，使订阅有意义。

```
                    ┌─ 主题：价格 ───┐
智能体 A ──发布──▶  │                │ ──▶ 智能体 D（已订阅）
                    ├─ 主题：订单 ───┤
智能体 B ──发布──▶  │                │ ──▶ 智能体 E（已订阅）
                    ├─ 主题：告警 ───┤
智能体 C ──发布──▶  │                │ ──▶ 智能体 F（已订阅）
                    └────────────────┘
```

### 各自何时胜出

- **完整池**适用于智能体少（< 10）、角色异构且会话短时程的情况。每个人看到一切时，推理“谁说了什么”很简单。
- **黑板**适用于智能体多、角色同质但实例数量多（群体）且会话长时间运行的情况。路由节约 token 成本并减少上下文污染。

生产系统常混用：顶部使用一个小型完整池（规划层），下方使用黑板（工作者层）。

### 一个记忆投毒场景

三个智能体共同做研究任务。A 是检索智能体，B 是摘要智能体，C 是分析师。

1. A 获取一个页面，向共享状态写入：“研究报告准确率提高 42%。”
2. 实际页面写的是“提高 4.2%”。A 幻觉掉了小数点。
3. B 读取共享状态后写入：“报告了巨大的 42% 准确率增益（来源：A）。”
4. C 读取共享状态后写入：“建议采用——42% 提升具有变革性。”
5. 最终报告引用了一个从未存在的 42% 数字。

没有智能体崩溃，没有测试失败，系统“正常工作”。幻觉通过共享状态从一个智能体的上下文进入所有下游智能体的推理，并被洗白为事实。

### 为什么这是结构性的

若没有共享状态，A 的幻觉会留在 A 的上下文中。下游智能体会重新获取或重新推导，或许能捕捉错误。朴素共享状态中，A 的上下文变成所有人的上下文，幻觉被洗白为事实。

问题不在共享状态本身，而在**没有来源信息且没有独立验证者**的共享状态。三种缓解措施能解决它：

1. **为每次写入附加来源信息。** 共享状态中的每条记录谁写、何时写、使用何种提示词，以及（如适用）智能体引用了什么来源。下游智能体根据来源信息保持怀疑。
2. **对写入做版本化；将其视为只追加。** 更正是一条取代旧记录的新记录，而不是原地更新。审计轨迹得以保留。
3. **至少保留一个不能写共享状态的智能体。** 只读验证者智能体抽样记录、重新获取来源并标记不一致。因为它不能写入池，不会被池投毒。

### 黑板先例（Hayes-Roth，1985）

黑板模式比 LLM 智能体早四十年。Hayes-Roth（1985 年，“A Blackboard Architecture for Control”）描述了观察全局黑板、贡献局部解并触发其他来源的专业知识源。2026 年的黑板（CA-MCP、Matrix）是相同模式，只是 LLM 智能体变成知识源、JSON blob 变成局部解。旧文献已经记录了现代系统正在重新发现的写入竞争、机会式控制和一致性解法。

### 投影视图与完整视图

纯黑板向每个订阅者提供同样的投影（按主题限定）。更激进的设计是**按智能体投影**：每个智能体得到按自己角色定制的视图。LangGraph 的状态 reducer 是 2026 年的规范实现——reducer 函数将全局状态折叠为角色专属切片。

按智能体投影扩展得更远，但需要模式。没有模式，你会在每个智能体的提示词中重建临时投影。

### 写入竞争模式 <!-- learning-atlas: write-contention-patterns -->

多个智能体同时写入属于并发问题，LLM 只是其中一个参与者。三种模式有效：

- **顺序写入者（单生产者）。** 所有写入经过一个协调智能体串行化。简单，但会成为瓶颈。
- **带版本的乐观并发。** 每条记录有版本；版本不匹配时写入者失败并重试。经典数据库技术。
- **主题分区。** 不同智能体拥有不同主题，没有跨主题竞争。需要精心设计分区边界。

多数 2026 年框架默认顺序写入者，因为 LLM 调用足够慢、竞争少，瓶颈的伤害也不大。

### 不可写验证者

最承重的缓解是只读验证者。实现规则：

- 验证者与团队共享状态（读取黑板或池）。
- 验证者没有共享状态的写句柄——只有单独验证通道的写句柄。
- 验证者独立获取写入中引用的来源，并标记分歧。
- 验证者的输出被路由给人类或单独决策智能体，绝不回灌进池。

没有这种隔离，验证者输出会成为池中的新记录，投毒池会投毒验证者，验证者又会投毒其验证。

## 动手构建

`code/main.py` 用标准库 Python 实现两种拓扑、一个玩具投毒攻击和三种缓解。

- `MessagePool`——线程安全、只追加且完整读出的日志。
- `Blackboard`——按主题键控的发布/订阅，支持按智能体订阅。
- `ProvenanceEntry`——每次写入记录 `(writer, timestamp, prompt_hash, source_uri)`。
- `PoisoningScenario`——运行三智能体研究任务，其中 A 幻觉一个小数点；打印最终报告。
- `Verifier`——重新获取来源并标记不一致的只读智能体；在有验证者时运行同一场景。

运行：

```
python3 code/main.py
```

预期输出：

- 第 1 次运行（无验证者）：幻觉的 42% 传播到最终报告。
- 第 2 次运行（有验证者）：验证者标记不一致，池被标为“flagged”，最终报告包含撤回。

## 实际使用

`outputs/skill-memory-auditor.md` 是一项技能，用于审计任意多智能体系统共享记忆的来源信息、版本控制和验证者隔离。新多智能体架构投产前运行它。

## 交付物

对任何共享记忆设计：

- 为每次写入记录来源：`(writer, timestamp, prompt_hash, tool_calls_cited, source_uri)`。
- 使日志只追加。更正是引用被取代记录的新条目。
- 部署至少一名拥有独立来源访问权的只读验证者智能体。
- 将验证者输出路由到独立通道，而非写回共享池。
- 记录写入中“取代”操作的比例——比例上升是幻觉模式的早期证据。

## 练习

1. 运行 `code/main.py`。确认第 1 次运行传播幻觉，第 2 次运行捕捉它。
2. 添加第二个幻觉：B 智能体编造数据集大小。验证者无需针对任一错误手调，也应能捕捉两者。
3. 将完整池换成带主题分区（`prices`、`summaries`、`analyses`）的黑板。主题分区使哪些投毒情形更难发生？对哪些无帮助？
4. 阅读 Hayes-Roth（1985 年，“A Blackboard Architecture for Control”）。找出论文中本课没有讨论、2026 系统会受益的两种控制模式。
5. 阅读 CA-MCP（arXiv:2601.11595）。将其 Shared Context Store 映射到 `code/main.py` 中的 MessagePool 或 Blackboard 类。CA-MCP 在其上添加了哪些原语？

## 关键术语

| 术语 | 常见说法 | 实际含义 |
|---|---|---|
| 消息池 | “共享聊天历史” | 每个智能体都读取的只追加日志；完全透明、扩展性差。 |
| 黑板 | “共享工作区” | 按主题键控的发布/订阅；智能体订阅相关主题，扩展更远。 |
| 来源信息 | “谁写了什么” | 每次写入的元数据：写入者、时间戳、提示词、来源。 |
| 记忆投毒 | “幻觉在传播” | 一个智能体的错误进入共享状态，下游智能体将其作为事实采纳。 |
| 只追加 | “不原地更新” | 更正是取代旧项的新记录，保留审计轨迹。 |
| 不可写验证者 | “独立审计者” | 重新获取来源、标记不一致的只读智能体。 |
| 投影 | “限定视图” | 由全局状态计算出的按智能体视图；LangGraph reducers 是规范案例。 |
| Knowledge Source | “专业智能体” | Hayes-Roth 1985 年对黑板参与者的称呼。 |
