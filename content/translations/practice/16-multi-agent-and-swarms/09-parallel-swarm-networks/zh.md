# 并行 / 群体 / 网络化架构

> 与主管模式相反：没有中心决策者。智能体读取共享事件总线，异步领取工作，并将结果写回。LangGraph 明确支持面向去中心化、动态环境的“Swarm Architecture”。Matrix（arXiv:2511.21686）将控制流和数据流都表示为经过分布式队列的序列化消息，以消除编排器瓶颈。取舍是明确的：用确定性和可追溯性换可扩展性。群体适合含有大量独立子问题的任务；不适合需要单一连贯计划的任务。

**类型：** 学习 + 构建
**语言：** Python（标准库，`threading`、`queue`）
**前置要求：** 第 16 阶段 · 05（主管模式），第 16 阶段 · 04（原语模型）
**用时：** 约 75 分钟

## 问题

主管可以扩展到少数工作者。数百名呢？主管本身成为瓶颈：每个“谁做什么”的决策都流经一个智能体。一个缓慢的规划步骤就会阻塞整个系统。

群体架构反转设计。不再由中心规划者派发工作，而由工作者从共享队列领取工作。“协调”被编码进事件总线语义。没有编排器；系统可扩展到队列成为瓶颈为止。

## 概念

### 形状

```
                ┌──── 共享队列 ────┐
                │                  │
       ┌────────┼────────┐  ◄──────┬───┘
       ▼        ▼        ▼         │
     工作者    工作者    工作者    工作者
      A         B         C         D
       │        │        │         │
       └────────┴────────┴─────────┘
                 │
                 ▼
              结果池
```

没有编排器。每名工作者重复：拉取一个任务、处理、写入结果（可选地将后续任务入队）。

### 群体何时适合

- **大量独立任务。** 抓取、转换、分类；任务之间不互相依赖。
- **时长可变的工作。** 若有些任务耗时 100ms，有些耗时 10 秒，群体会自动均衡负载——快工作者继续领取下一项。主管必须预估时长。
- **吞吐量高于确定性。** 你关心总完成时间，而非严格顺序。

### 群体何时失败

- **有序工作流。** 若第 3 步需要第 2 步输出，群体可能在第 2 步完成前触发第 3 步。
- **全局规划任务。** 复杂研究问题会受益于规划者；研究者群体会产出独立事实，而非连贯报告。
- **调试。** 没有中心日志且工作异步时，复现 bug 代价很高。

### Matrix（arXiv:2511.21686）

Matrix 是 2025 年论文，它将群体推到自然结论：控制流和数据流都是分布式队列上的序列化消息，没有中心协调者。容错来自消息持久性；可扩展性是消息代理的问题，而不是系统的问题。

其贡献是一个编程模型：多智能体协调变成“该智能体订阅哪个消息主题？”，而不是“主管下一步选哪个智能体？”。这让系统看起来像发布/订阅事件网格。

### 图框架中的群体

LangGraph 2025 年文档明确将“Swarm Architecture”描述为多智能体模式之一：智能体是节点，但边构成带循环的有向图，池中的任意节点都可被激活。工作者依据条件从可用工作中领取，而非由主管分配。

### 失效模式：饥饿与热点

若所有工作者都拉取最快可用任务，长时间任务在只剩它们之前永远不会被领取，这属于经典队列饥饿。

缓解措施：

- 带显式老化的优先级队列（随等待时间提高优先级）。
- 工作者专业化：部分工作者只接“长”任务。
- 背压：限制有多少快速任务能进入队列。

### 基于内容的路由关联

群体天然适配基于内容的路由（第 22 课）。不要用一个通用队列，而应为每种消息类型设置一个队列。专业工作者只订阅自己的类型，这构成可扩展至数千个智能体的消息总线架构基础。

## 动手构建

`code/main.py` 实现一个由 4 个工作线程组成的群体，它们从共享 `queue.Queue` 拉取任务。任务时长可变（有些快，有些慢）。演示对比：

- **顺序基线：** 一名工作者串行处理所有任务。
- **固定分配：** 每项任务预先分配给某名特定工作者（主管式）。
- **群体：** 工作者从共享队列领取。

群体自动均衡负载；固定分配中，已分配慢任务时快工作者会空闲。

运行：

```
python3 code/main.py
```

输出展示每名工作者的任务数（群体分配不均但最优）及墙钟时间。

## 实际使用

`outputs/skill-swarm-fit.md` 评估一项任务应使用群体还是主管。输入：任务独立性、时长方差、排序要求、可调试性需求。

## 交付物

检查表：

- **带老化的优先级队列。** 防止长任务饥饿。
- **工作者幂等性。** 若工作者运行中崩溃，任务可能被领取多次。工作者必须幂等。
- **持久队列。** 生产使用 Kafka、Redis Streams 或数据库支持的队列。`queue.Queue` 仅在内存中。
- **每任务可观测性。** 每个任务拥有 trace ID；每名工作者都记录带该 ID 的开始/结束。
- **背压。** 若队列增长快于工作者排空，就减慢生产者。

## 练习

1. 运行 `code/main.py`。在时长可变的工作负载上，群体比顺序快多少？比固定分配快多少？
2. 加入优先级队列变体（使用 `queue.PriorityQueue`）。按任务“重要性”字段设置优先级。观察连续负载下低优先级任务是否会饥饿。
3. 实现热点检测器：当任一工作者处理的任务数为最慢工作者的 3 倍时记录。它说明任务时长分布的什么？
4. 阅读 Matrix 论文（arXiv:2511.21686）的摘要和第 3 节。找出 Matrix 接受的一项具体取舍（可扩展性增益）与它放弃的一项（可追溯性、确定性）。
5. 将群体演示转换为使用 `(task_type, payload)` 元组构成的 `queue.Queue`，工作者只订阅特定类型。任务异构时，什么路由规则有意义？

## 关键术语

| 术语 | 常见说法 | 实际含义 |
|---|---|---|
| 群体架构 | “去中心化智能体” | 工作者从共享队列拉取任务；没有中心编排器。 |
| 事件总线 | “智能体订阅主题” | 按类型或内容将任务路由给工作者的消息代理。 |
| 饥饿 | “任务永不运行” | 因高优先级工作持续到达，低优先级任务永远不会被领取。 |
| 热点 | “一个工作者被淹没” | 一名工作者拿到大多数任务的负载不均。 |
| 背压 | “减慢生产者” | 队列填满时通知上游停止生产的机制。 |
| 幂等工作者 | “可安全重跑” | 同一任务处理两次也产生相同结果；工作者可能中途崩溃，因而必需。 |
| 持久队列 | “崩溃后仍存在” | 由磁盘或复制存储支撑的队列；工作者崩溃时任务不会丢失。 |
| Matrix 框架 | “完整消息传递群体” | 数据流和控制流都以分布式队列中的序列化消息表示。 |
