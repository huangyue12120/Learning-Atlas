# 层级架构及其失效模式

> 层级架构就是嵌套的主管：管理智能体统领子管理者，子管理者统领工作者。CrewAI 的 `Process.hierarchical` 是教科书式版本：`manager_llm` 动态委派任务并验证输出。LangGraph 的等价形式是 `create_supervisor(create_supervisor(...))`。当任务确实对应一张组织架构图时，它是自然模式；它也是最可能坍缩为管理循环的模式——管理智能体错误分配工作、误解子输出，或无法达成共识。顺序模式往往更好。

**类型：** 学习 + 构建
**语言：** Python（标准库）
**前置要求：** 第 16 阶段 · 05（主管模式）
**用时：** 约 60 分钟

## 问题

一旦理解主管模式，自然的下一步便是“如果工作者本身也是主管呢？”团队有子团队，公司有部门之上的部门。层级架构映射这种结构。

问题在于：LLM 管理者不同于人类管理者。人类管理者对下属掌握什么具有稳定先验；LLM 管理者每一轮都只能用其上下文中的内容重新推理组织结构。上下文发生微小漂移，整棵树都会错误分配工作。

## 概念

### 形状

```
                 管理者
                 ┌─────┐
                 └──┬──┘
           ┌────────┴────────┐
           ▼                 ▼
       子经理 A          子经理 B
       ┌─────┐           ┌─────┐
       └──┬──┘           └──┬──┘
         ┌┴──┬──┐          ┌┴──┐
         ▼   ▼  ▼          ▼   ▼
       W1  W2  W3         W4  W5
```

每一个内部节点都规划、委派和综合，只有叶子节点真正做工作。

### 擅长之处

- **清晰的组织映射。** 若真实任务是按部门划分的（“法务审阅文档、财务审阅文档、工程审阅文档，再为高管总结”），层级结构是明确的。
- **局部综合。** 每名子管理者在顶层管理者看到之前先综合团队输出。顶层管理者只看到三份子管理者摘要，而不是十五份工作者输出。

### 崩溃之处

2026 年复盘不断发现三种失效模式：

1. **任务分配错误。** 管理者读到目标后虚构一个分解，并委派给错误的子管理者。子管理者会顺从地完成得到的工作，因此错误只会在顶层综合时显现——距离人类本可发现的位置又隔了一层。
2. **输出误解。** 子管理者返回“无法验证声明 X”，顶层管理者总结为“声明 X 未获确认”。含义在每一级漂移。
3. **共识循环。** 两名子管理者不同意；顶层管理者让他们协调；他们又向下委派；工作者重跑；子管理者返回略有不同的答案；如此循环。CrewAI 的 `Process.hierarchical` 用步数上限防护，但这个上限本身现在成了超参数。

### 决定性问题

顺序（线性流水线）还是层级：你的任务确实存在独立子团队，还是把一个线性流程假扮成树？若是后者，用顺序；若是前者，用层级，但要为显式协调规则预算。

### 角色框架实现

CrewAI 的 `Process.hierarchical` 在专业团队之上连接一个管理 LLM。管理者：

- 接收顶层任务，
- 将子任务分配给团队，
- 评估团队输出，
- 决定接受、重新委派还是迭代。

文档：https://docs.crewai.com/en/introduction（在 Core Concepts 下查找 “Hierarchical Process”）。

### 图框架实现

LangGraph 使用嵌套 `create_supervisor` 调用。内部主管拥有自己的图；外部主管将内部图视为不透明节点。这比 CrewAI 更利于调试（可分别逐步执行每张图），但更难表达树的动态重塑。

参考：https://reference.langchain.com/python/langgraph-supervisor。

## 动手构建

`code/main.py` 运行一个三层层级：

- 顶层管理者：将任务拆成“工程”和“法务”分支，
- 工程子管理者：拆成“前端”和“后端”工作者，
- 法务子管理者：一名工作者。

演示将顺利路径（所有人都同意）与**扰动路径**对比：顶层管理者的分解将“法务”错标为“财务”，然后观察错误级联——子管理者顺从地做财务工作，顶层综合器报告财务发现，原本的法务问题无人回答。

运行：

```
python3 code/main.py
```

输出清晰并排展示两条路径中的“请求了什么”与“交付了什么”。

## 实际使用

`outputs/skill-hierarchy-fitness.md` 评估给定任务应使用层级、顺序还是扁平主管模式。输入为任务描述、组织结构、协调预算；输出为模式建议及要防护的具体失效模式。

## 交付物

若要交付层级架构：

- **将树深限制为 2。** 三层已经会把大部分错误藏到可观测性之外。
- **明确协调预算。** 在顶层管理者必须提交前设定最大轮数，通常为 2。
- **每次综合保留来源。** 每个节点的摘要必须引用产生它的叶子输出。
- **对分解漂移告警。** 每一步记录管理者的分解，并与用户查询做差异比较。若分解不再覆盖查询，触发告警。

## 练习

1. 运行 `code/main.py`，比较顺利与扰动路径。经过多少层管理交接，顶层输出才会完全偏离用户问题？
2. 添加第三层（顶层 → 子层 → 子子层 → 工作者）。随着深度增加，测量扰动路径自我纠正和完全发散的频率。
3. 为每位子管理者实现一个“金丝雀”工作者，它始终接收未经改变的原始用户问题。用金丝雀回答检测分解漂移。当金丝雀不同意综合答案时，管理者应如何反应？
4. 阅读 CrewAI 的 `Process.hierarchical` 文档。找出 CrewAI 应用的一项具体护栏（步数上限、`manager_llm` 约束），并说明它针对的失效模式。
5. 比较嵌套的 LangGraph 主管和 CrewAI 层级。哪种更容易发现协调循环？

## 关键术语

| 术语 | 常见说法 | 实际含义 |
|---|---|---|
| 层级 | “组织架构图模式” | 主管之上的主管；只有叶子节点做具体工作。 |
| 管理 LLM | “老板” | 在内部节点分解、分配和验证的 LLM。 |
| 分解漂移 | “老板跑题了” | 顶层管理者的拆分不再覆盖原始问题。 |
| 协调循环 | “无休止的会议” | 子管理者不同意；顶层重新委派；工作者重跑；直到预算耗尽。 |
| 深度 2 上限 | “不要超过 2 层” | 经验性护栏：3 层以上会使可观测性坍缩。 |
| 金丝雀问题 | “每层的事实基准” | 始终收到不变原始查询、用来检测漂移的工作者。 |
| 来源链 | “谁说了什么” | 从每次综合回溯到产生它的叶子输出的跟踪。 |
