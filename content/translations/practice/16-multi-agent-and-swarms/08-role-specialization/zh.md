# 角色专业化——规划者、批评者、执行者、验证者

> 2026 年最常见的多智能体分解：一个智能体规划，一个执行，一个批评或验证。MetaGPT（arXiv:2308.00352）将其形式化为编码进角色提示词的 SOP：产品经理、架构师、项目经理、工程师、QA 工程师，并遵循 `Code = SOP(Team)`。ChatDev（arXiv:2307.07924）通过“聊天链”串联设计师、程序员、审阅者、测试者，并使用“沟通式去幻觉”（智能体显式请求缺失细节）。验证者是承重角色：Cemri 等人（MAST，arXiv:2503.13657）表明，每一种多智能体失效都可追溯到缺失或损坏的验证。PwC 报告，CrewAI 中的结构化验证循环可将准确率从 10% 提升至 70%，增益为 7 倍。

**类型：** 学习 + 构建
**语言：** Python（标准库）
**前置要求：** 第 16 阶段 · 04（原语模型），第 16 阶段 · 05（主管）
**用时：** 约 60 分钟

## 问题

通用多智能体系统会产生通用输出。群聊中的三名编码者会写出三种版本、同样平庸的代码。你可以增加更多智能体、增加更多轮次，仍然跨不过质量阈值。

系统需要承担不同角色的智能体。分配明确角色，让批评者获得规划者没有的工具，让验证者获得客观测试套件。此时系统拥有带有依据的内部异议与纠正，也不再只是并行猜测。

## 概念

### 四种规范角色

**规划者。** 阅读目标，产出步骤清单或规格。工具：知识检索、文档。输出：结构化计划。

**执行者。** 一次阅读一个计划步骤，产出制品。工具：真正的工作工具（代码编译器、shell、API 客户端）。输出：制品。

**批评者。** 对照规划者意图阅读执行者输出。工具：对制品的只读访问、静态分析。输出：带理由的接受/拒绝。

**验证者。** 阅读制品并运行确定性检查。工具：测试运行器、类型检查器、模式验证器。输出：带证据的通过/失败。

批评者主观、有观点，常基于 LLM。验证者客观、确定，常基于代码。它们不是同一角色。

### MetaGPT 的 SOP 模式

MetaGPT（arXiv:2308.00352）将软件工程 SOP 编码为角色提示词：

- **产品经理**撰写 PRD。
- **架构师**产出系统设计。
- **项目经理**拆分任务。
- **工程师**实现。
- **QA 工程师**运行测试。

每个角色都有严格的输入/输出模式。角色提示词说明角色*是什么*及其*必须产出什么*。`Code = SOP(Team)` 的表述意味着：确定性的 SOP 将一群 LLM 变为可预测的流水线。

### ChatDev 的沟通式去幻觉

ChatDev 加入一个关键动作：当执行者需要计划中没有提供的具体细节时，它会在继续前明确询问设计者。这避免了 LLM 似是而非地虚构细节的经典失败。

实现：角色提示词应包含“当你需要未获得的特定信息时，在产出前按名称询问相关角色”。

### 为什么验证者最重要

Cemri 等人（MAST）追踪了 1642 起多智能体执行失败。其中 21.3% 是验证缺口——系统交付了未经任何人检查的答案。其余 79% 往往也可追溯到“存在一个静默失败或从未运行的检查”。验证是承重角色。

PwC 报告（CrewAI 部署，2025），增加结构化验证循环使准确率从 10% 升到 70%。一个角色带来 7 倍增益。

### 批评者与验证者

- 批评者是审阅制品质量的 LLM，主观，可能被看似合理的文字愚弄。
- 验证者是在制品上运行的确定性程序，客观，给出带证据的通过/失败。

两者都要用。批评者能捕捉验证者无法表达的品味问题；验证者能捕捉批评者看不见、只在运行时出现的错误。

### 反模式

系统中的每个角色都是 LLM，而每个角色的输出都是“我看起来觉得不错”。这属于经典 MAST 失效模式。至少加入一个其通过/失败由代码而非 LLM 决定的验证者。

### 框架映射

- **CrewAI**——`Agent(role, goal, backstory)` 是教科书式的专业化表面。
- **LangGraph**——节点可使用专业提示词；边强制流水线。
- **AutoGen**——GroupChat 中带一词名称的角色专用 ConversableAgents。
- **OpenAI Agents SDK**——角色专用 Agents 之间的交接工具。

## 动手构建

`code/main.py` 实现一个构建简单 Python 函数的四角色流水线：

- **规划者**产出规格。
- **执行者**生成代码字符串。
- **批评者**（LLM 模拟）标记明显问题。
- **验证者**在沙箱（`exec`）中针对测试用例运行生成的代码。

演示运行两次：一次执行者生成正确代码（批评者和验证者都通过）；一次执行者生成偏离规格的代码（批评者因其看似合理而漏掉 bug，验证者因测试失败而捕捉它）。

运行：

```
python3 code/main.py
```

## 实际使用

`outputs/skill-role-designer.md` 接收任务并产出角色名册（3–5 个角色）、每个角色的输入/输出模式，以及验证者检查。将智能体接入框架前使用它。

## 交付物

检查表：

- **至少一个确定性验证者。** 绝不能全是 LLM。
- **每个角色明确 I/O 模式。** 规划者返回规格，而不是散文；执行者读取该模式。
- **沟通式去幻觉。** 信息缺失时执行者必须询问规划者，绝不虚构。
- **批评者/验证者顺序。** 先运行批评者（便宜，捕捉设计问题），再运行验证者（慢，捕捉 bug）。
- **循环预算。** 最多 2 轮批评者—执行者修订，之后升级给人类。

## 练习

1. 运行 `code/main.py`，观察验证者如何捕捉批评者遗漏的 bug。增加静态分析检查（统计 `return` 出现次数）作为额外验证者。它能捕捉运行时测试遗漏的什么？
2. 加入第 5 个角色：“需求分析师”，将用户愿望转为规划者可用的规格。应向它发起哪些沟通式去幻觉请求？
3. 阅读 MetaGPT 第 3 节（“Agents”）。列出 MetaGPT 五个角色各自的输入/输出模式。
4. 阅读 ChatDev 的聊天链图（arXiv:2307.07924 图 3）。找出沟通式去幻觉在哪一处打断了本会无限进行的循环。
5. PwC 的 7 倍准确率增益来自验证循环。假设三类增加验证者无帮助的任务——其中的正确性确定性检查不可能或成本高得无法承受。

## 关键术语

| 术语 | 常见说法 | 实际含义 |
|---|---|---|
| 角色专业化 | “不同智能体，不同工作” | 为规划者/执行者/批评者/验证者角色调优的不同系统提示词。 |
| SOP 模式 | “编码的标准作业程序” | MetaGPT 的框架：每个角色的严格 I/O 模式将团队变为流水线。 |
| 沟通式去幻觉 | “先问再编” | ChatDev 模式：细节缺失时执行者询问规划者，而不是自行编造。 |
| 批评者 | “LLM 审阅者” | 主观、有观点的审阅者；捕捉品味问题，可能被合理文字愚弄。 |
| 验证者 | “确定性检查” | 基于代码的通过/失败；测试运行器、类型检查器、模式验证器；不可被愚弄。 |
| 验证缺口 | “没人检查” | 21.3% 的 MAST 失败；未经本可捕捉 bug 的检查便交付答案。 |
| 修订循环 | “批评者打回” | 批评者拒绝会触发执行者带反馈重跑；需要预算。 |
| 全 LLM 反模式 | “我看起来觉得不错” | 每个角色都是 LLM，没有确定性检查；经典 MAST 失败。 |
