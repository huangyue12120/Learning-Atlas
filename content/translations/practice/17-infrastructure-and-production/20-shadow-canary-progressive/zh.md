# LLM 的影子流量、金丝雀发布与渐进式部署

> LLM 发布结合了软件部署中最困难的部分：没有单元测试、失败模式分散、信号延迟。顺序为：(1) 影子模式——将生产请求复制给候选模型、记录并比较，对用户零影响；能捕获明显的分布问题，但不是质量保证；(2) 金丝雀发布——逐步转移流量 10% → 25% → 50% → 75% → 100%，每一步都设闸；跟踪延迟百分位数、每请求成本、错误/拒绝率、输出长度分布、用户反馈率；(3) 稳定性确认后，对明显不同的备选方案做 A/B 测试。非确定性无法消除——由于 GPU FP 非结合性加上 batch size 方差，相同输入的跨次准确率变化可达 15%。成本是变量而非常数——好 20% 的模型单次调用成本可能高 3 倍。回滚速度最关键：若回滚需要重新部署，你就太慢了。策略存在 config/flags 中，模型以固定 digest 存在 registry 中；回滚 = 翻转策略 + 恢复阈值 + 固定旧模型，只需数秒。

**类型：** 学习
**语言：** Python（标准库，用于模拟金丝雀推进的玩具程序）
**前置要求：** 第 17 阶段 · 13（可观测性），第 17 阶段 · 21（A/B 测试）
**用时：** 约 60 分钟

## 学习目标

- 区分影子模式（零影响比较）、金丝雀（实时流量渐进）和 A/B（稳定性确认后的比较）。
- 枚举五项 LLM 专属金丝雀指标（延迟、每请求成本、错误/拒绝、输出长度分布、用户反馈）。
- 解释为什么 LLM 非确定性（最高 15%）改变了发布中“稳定”的含义。
- 设计耗时数秒（策略翻转）而非数小时（重新部署）的回滚路径。

## 问题

你发布一个新模型。离线评估显示准确率提升 3%，你在生产中打开它。24 小时内，成本上升 40%，用户点踩上升 8%，三张客户工单报告“奇怪的回答”。你回滚，重新部署耗时 3 小时，周末被毁。

每一件事都可以避免。影子模式会在用户看到它之前捕获 40% 成本尖峰；金丝雀会在 10% 时于点踩变化处停下；策略标志回滚只需 30 秒。这种纪律填补了“离线评估很好看”与“真实用户满意”之间的空白。

## 概念

### 影子模式

候选模型接收与生产相同的请求；输出被记录，不返回用户。对用户零影响。记录：

- 输出内容（与生产输出比较）。
- Token 数（成本增量）。
- 延迟。
- 拒绝和错误。

能捕获：成本爆炸、长度回归、明显拒绝变化、严重错误。不能捕获：用户会感知到的质量差异。影子模式是冒烟测试，不是质量测试。

### 金丝雀发布

带闸的渐进式流量转移。典型推进：1% → 10% → 25% → 50% → 75% → 100%。每一步对 5 项指标设闸：

1. **延迟百分位数**——P50、P95、P99。违规：金丝雀 P99 > 基线 1.5 倍。
2. **每请求成本**——混合 $。违规：比基线高 >20%。
3. **错误 / 拒绝率**——5xx 加显式拒绝。违规：基线 2 倍。
4. **输出长度分布**——平均 + P99。违规：发生分布移位。
5. **用户反馈率**——点踩 / 提交工单。违规：基线 1.5 倍。

### 非确定性是新的方差

相同输入会产生不同输出，原因是：

- GPU FP 非结合性（浮点归约顺序随 batch 而变）。
- Batch size 方差（同一提示词处于 128 批次或 16 批次）。
- 采样（temperature > 0）。

测得：相同评估集跨次运行的准确率变化最高可达 15%。发布中的“稳定”指指标处于预期方差内，而非与基线完全一致。将闸门设置在噪声底线之上。

### 成本是变量

好 20% 的模型单次调用成本可能是 3 倍。每请求成本是五项闸门之一。发布“更好”却破坏单位经济性的模型，应当回滚。

### 回滚是武器

- 策略标志（feature flag 系统）：翻转 config 中的百分比，耗时数秒。
- 模型固定（registry digest）：固定模型不会自动升级。
- 回滚 = 恢复标志 + 将固定 digest 设为上一版本。数秒，而非数小时。

若你的栈必须重新部署才能回滚，应在发布之前修复它。

### 工具

**Argo Rollouts** / **Flagger**——Kubernetes 渐进式交付控制器，与 Istio/Linkerd 的加权路由集成。

**Istio 加权路由**——服务网格层的流量拆分。

**KServe / Seldon Core**——内置金丝雀的模型服务。

**Feature flags**——LaunchDarkly、Flagsmith、Unleash。策略层翻转，无需重新部署。

### 指标节奏

金丝雀闸门每 5–15 分钟检查一次，取决于流量。每分钟 10 个请求的 1% 流量，每窗口有 50–150 个数据点——足以测延迟，却对用户反馈很嘈杂。10% 可得到约 10 倍数据。推进应暂停足够久，使每一步累积足够样本。

### A/B 步骤是可选的

若新模型明显不同（行为不同、成本曲线不同、语调不同），金丝雀通过后在 50% 做 A/B。若它仅是改进版本，则在金丝雀闸门通过后直接升至 100%。

### 应当记住的数字

- 金丝雀推进：1% → 10% → 25% → 50% → 75% → 100%。
- 非确定性上限：相同输入跨次方差最高 15%。
- 五项金丝雀指标：延迟、成本、错误/拒绝、输出长度、用户反馈。
- 成本闸门：比基线高 >20% 即违规。
- 回滚：数秒，而非数小时。

## 关键术语

| 术语 | 人们怎么说 | 实际含义 |
|------|-----------|----------|
| 影子模式 | “复制给新模型” | 将请求零影响发送给候选模型以记录 |
| 金丝雀 | “渐进流量” | 带闸的、逐步暴露给用户的发布 |
| 闸门 | “发布检查” | 阻止推进的指标阈值 |
| 非确定性 | “LLM 方差” | 无法消除的跨次运行差异 |
| 策略标志 | “标志翻转回滚” | 配置层回滚，数秒而非数小时 |
| 模型固定 | “registry digest” | 对模型版本的不可变引用 |
| Argo Rollouts | “K8s 渐进式” | Kubernetes 原生金丝雀/回滚控制器 |
| KServe | “推理 K8s” | 带金丝雀原语的模型服务 |
| Istio 加权 | “网格拆分” | 服务网格流量分流器 |
