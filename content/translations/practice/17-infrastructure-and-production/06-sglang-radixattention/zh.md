# 前缀缓存服务：RadixAttention 与 KV 复用

> 将 KV 缓存视为存放在基数树中的一等、可复用资源，调度会随之改变：vLLM 使用 FCFS（先到先服务），而缓存感知调度器会优先处理共享更长前缀的请求——本质上是深度优先的基数遍历，以使热点分支保留在 HBM。SGLang 是围绕这个思想构建服务的引擎。在具有 ShareGPT 风格 1K 提示词的 Llama 3.1 8B 上，SGLang 达到约 16,200 tok/s，vLLM 为约 12,500，即约 29% 优势；在前缀密集 RAG 工作负载上优势达到 6.4 倍；在语音克隆形状的工作负载上，缓存命中率超过 86%。到 2026 年，它已部署在 xAI、LinkedIn、Cursor、Oracle、GCP、Azure、AWS 的 40 万+ GPU 上。前缀顺序不一致时，6.4 倍会消失；排序就是工程师手中的杠杆。

**类型：** 学习
**语言：** Python（标准库，玩具基数树缓存 + 缓存感知调度器）
**前置要求：** 第 17 阶段 · 04（服务引擎内部机制），第 14 阶段（智能体 RAG）
**用时：** 约 75 分钟

## 学习目标

- 绘制 RadixAttention：前缀如何存入基数树，以及同一分支根下的序列如何共享 KV 块。
- 解释缓存感知调度，以及为何 FCFS 对前缀密集流量是错误选择。
- 给定前缀缓存命中率与提示词长度分布，计算工作负载的期望加速。
- 说出使 6.4 倍成为现实而不是损失机会的提示词排序纪律。

## 问题

经典服务将每个请求的提示词视为不透明。即使 5,000 个 RAG 请求都以相同的 2,000-token 系统提示词和相同检索前言开头，vLLM 仍会将这段 2,000-token 前缀 prefill 5,000 次。GPU 重复做同一项工作。

观察是：智能体和 RAG 工作负载中的提示词几乎总共享长前缀。系统提示词、工具模式、few-shot 示例、检索头、对话历史——都会跨请求重复。若将该前缀的 KV 缓存存一次并复用，就不必再 prefill。

RadixAttention 正是这样做。Token 被索引在基数树中，每个节点拥有从根到自身路径上 token 序列的 KV 块。新请求会遍历这棵树：只要节点 token 匹配，就复用该节点的 KV 块。Prefill 成本变为“新”后缀的成本，而不再是完整提示词的成本。

挑战在调度。如果两个请求共享 2,000-token 前缀，第三个仅共享同一前缀中的 200 token，你希望将两个长共享请求一起服务，以让长前缀留在 HBM。FCFS 恰好相反——先服务先到者，可能在下一个长前缀请求到达前驱逐热点分支。

## 概念

### 作为 KV 索引的基数树

基数树（压缩 trie）存储 token 序列。每个节点拥有一个 token 范围和为该范围计算出的 KV 块，子节点将序列延长一个或多个 token。

```
root
 |- “你是一个乐于助人的助手……”  （2,000 token，124 个 KV 块）
      |- “上下文：<文档 A>……”      （500 token，31 个块）
           |- “问题：Alice……”       （80 token，5 个块）
           |- “问题：Bob……”         （95 token，6 个块）
      |- “上下文：<文档 B>……”      （520 token，33 个块）
```

一个新请求带着系统提示词 + “上下文：<文档 A>” + “问题：Carol”到来。调度器遍历：系统前缀匹配（复用 124 块），文档 A 分支匹配（复用 31 块），随后只为“问题：Carol”分配新块（4 块）。Prefill 成本为 4 块新 token；没有树时为 160 块，对 prefill 节省约 40 倍。

### 缓存感知调度

如果缓存不断抖动，基数树支持的复用毫无意义。两条关键策略：

1. **深度优先派发。** 从队列选择下一个请求时，优先选择与当前运行集合位于同一分支根的请求，令热点分支保持固定。
2. **分支级 LRU，而非块级 LRU。** 驱逐整个分支（从最久未用的叶开始），而非单独驱逐块，使缓存形状与基数形状匹配。

FCFS 违反二者。一个共享 2,000 token 的请求会排在共享 50 token 的请求之后，随后为接纳后者而驱逐 2,000-token 分支。

### 应记住的基准数字

- Llama 3.1 8B、H100、ShareGPT 1K 提示词：SGLang 约 16,200 tok/s，vLLM 约 12,500（约 29% 优势）。
- 前缀密集 RAG（相同系统 + 相同文档、问题不同）：SGLang 最多 6.4 倍。
- 语音克隆工作负载：86.4% 前缀缓存命中率。
- SGLang 客户的生产命中率：取决于提示词纪律，介于 50–99%。
- 2026 年部署在 40 万+ GPU 上。

### 排序陷阱

6.4 倍依赖一致的提示词模板排序。若客户端在某些请求中构造 `[system, tools, context, history, question]`，另一些则构造 `[system, context, tools, history, question]`，树无法找到共享前缀。对人类看似共享前缀，对基数树却是两条不同序列。

工程师的杠杆：提示词模板就是缓存键。固定顺序，将一切不可变内容（系统、工具、模式）放在前面，检索上下文放在后面，用户问题放在最后。不要将动态内容交错插入前缀。

研究中的真实案例是：将动态内容移出可缓存前缀后，一次部署通过一项变更就将缓存命中率从 7% 提升至 74%。

### RadixAttention 在哪里取胜和失败

取胜场景：

- RAG（相同检索前言、不同问题）。
- 智能体（相同工具模式、不同查询）。
- 具有长系统提示词的聊天。
- 具有重复前言的语音/视觉工作负载。

失败（回到 vLLM 级吞吐）的场景：

- 具有唯一提示词的单次生成（代码补全、无系统提示词的开放聊天）。
- 每个请求都将唯一内容交错到前缀中的动态提示词。

### 为什么这是调度问题，而不只是内核问题

你可以将 KV 复用实现为内核技巧。SGLang 的洞见是：只有调度器令热点分支保留时，复用才会回报。朴素的“可用即复用”策略会在混合负载下抖动缓存。以基数树为索引的调度器，才将内核技巧转化为 29% 的生产优势。

### 与 vLLM 的互相作用

两个系统并非严格竞争者。2026 年 vLLM 增加了前缀缓存（`--enable-prefix-caching`）和缓存感知路由器（Rust 编写的 vLLM Router）。差距缩小但未完全消失：SGLang 整个栈以基数为先，vLLM 是后加。对于以前缀复用为主的工作负载，SGLang 仍是默认选择；对于没有强前缀模式的通用服务，vLLM 仍然相当或更好。

## 使用

`code/main.py` 实现玩具基数树 KV 缓存和两种调度策略：FCFS 与缓存感知。它将相同工作负载跑过两者，报告前缀缓存命中率和吞吐量差；随后运行“打乱排序”工作负载，展示 6.4 倍如何崩塌。

## 交付

本课产出 `outputs/skill-radix-scheduler-advisor.md`。给定工作负载描述（提示词模板形状、检索模式、并发租户数），它会给出提示词排序方案和采用 SGLang 的 go/no-go 建议。

## 练习

1. 运行 `code/main.py`。在同一工作负载上比较 FCFS 与缓存感知策略。差异来自 prefill 节省、decode 节省，还是队列延迟？
2. 修改工作负载，让提示词随机排列 `[system, tools, context]`，重新运行。命中率会怎样，为什么？
3. 计算在 Llama 3.1 8B 上将 2,000-token 系统提示词作为一个基数分支留在 HBM 的成本，并与未复用前缀的 16 序列批次成本比较。
4. 阅读 SGLang RadixAttention 论文。用三句话解释，为何树形 LRU 驱逐在前缀密集负载下胜过块形 LRU。
5. 客户报告缓存命中率只有 8%。说出三种可能原因，以及你会为每种运行的诊断。

## 关键术语

| 术语 | 常见说法 | 实际含义 |
|------|----------|----------|
| RadixAttention | “SGLang 那个东西” | 以基数树索引 KV 缓存，使共享前缀复用块。 |
| 基数树 | “压缩 trie” | 每个节点拥有 token 范围及对应 KV 块的树。 |
| 缓存感知调度器 | “热点分支优先” | 优先处理与驻留分支共享的请求的调度器。 |
| 前缀缓存命中率 | “提示词有多少免费” | 从复用 KV 块获得服务的提示词 token 比例。 |
| FCFS | “先到先服务” | 破坏前缀局部性的默认调度。 |
| 分支级 LRU | “驱逐叶子” | 与基数形状匹配的驱逐策略。 |
| 提示词模板排序 | “缓存键” | 提示词组成部分的顺序决定树能共享什么。 |
| 系统提示词固定 | “驻留前缀” | 让不可变系统部分保持固定，以避免驱逐抖动。 |
