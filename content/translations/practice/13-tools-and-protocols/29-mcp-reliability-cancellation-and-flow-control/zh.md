# MCP 可靠性、取消与流量控制

> 请求 ID 能关联消息，但不能让副作用变得安全、停止 worker，或保护流式连接免受慢消费者影响。

**类型：** 构建
**语言：** Python
**前置课程：** Phase 13 · 第 09、13 课
**预计时间：** 约 120 分钟

## 学习目标

- 为 stdio 和 Streamable HTTP 实现正确的取消信号。
- 解决完成与取消之间的竞态，取消后不再发送消息。
- 区分请求取消与持久化 `tasks/cancel` 语义。
- 根据副作用和显式幂等键制定重试决策。
- 在保留最终响应的同时限制进度队列大小。
- 通过重连、重新获取和带抖动的退避恢复流。

## 问题所在

快乐路径会掩盖分布式系统中代价最高的 bug。

客户端调用工具。服务器开始工作。进度到达。代理缓存了流。客户端超时并断开连接。服务器在一毫秒后完成。客户端用新的 JSON-RPC id 重试。变更操作执行了两次。

每个组件在本地看起来都正常，但系统整体失败了。

MCP 定义消息和传输行为，但以下部分仍由应用负责：

- 时间预算；
- 业务幂等性；
- 有界队列；
- 重试分类；
- 持久化任务状态；
- 重连和重新获取策略。

本课把这些决策构建到一个确定性模拟器中。模拟器没有 sleep、socket 或随机失败；你可以直接控制取消事件的顺序。一个同步线程测试会强制两个账本客户端竞争同一个幂等键。

## 请求取消取决于传输方式

所有传输方式的意图相同：客户端不再需要正在执行的结果。但线上信号不同。

### stdio

stdio 使用一个共享的双向通道。客户端发送通知：

```json
{
  "jsonrpc": "2.0",
  "method": "notifications/cancelled",
  "params": {
    "requestId": 41,
    "reason": "User closed the operation"
  }
}
```

该通知是发出即忘的；服务器不会为它发送 JSON-RPC 响应。

服务器应停止工作、释放资源，并避免为已取消的请求发送响应。如果请求未知、已经完成，或无法安全停止，服务器可以忽略取消。

格式错误、未知请求以及已经完成请求的取消通知都应被忽略。把这些竞态转换成新的错误，只会制造更多竞态。

### Streamable HTTP

现代 Streamable HTTP 为每个请求提供独立的 HTTP 响应流或 SSE 响应流。客户端通过关闭该请求的响应流来取消。

普通 HTTP 请求不要 POST `notifications/cancelled`。关闭流就是取消信号。

服务器观察到断开连接后，应停止工作，并且不得再为该请求发送消息。

### 服务器发出的取消范围很窄

服务器不会使用 `notifications/cancelled` 去取消任意客户端调用。在 stdio 上，服务器发出的取消仅用于终止 `subscriptions/listen` 请求。应把这条路径与普通的客户端请求取消分开。

## 取消是一个竞态

两种事件顺序都合法。

### 取消获胜

```text
request starts
client sends cancellation signal
server marks request cancelled
worker reaches completion
server suppresses the response
```

### 完成获胜

```text
request starts
worker commits the result
server sends the response
cancellation arrives late
server ignores the late notification
```

客户端也必须忽略它已经放弃的请求的迟到响应。由于网络延迟，任何一方都不能证明另一方先观察到了哪一个事件。

```figure
mcp-reliability-race
```

本课的 `RequestCoordinator` 保存一个终态。取消之后调用 `complete()` 不会返回响应；迟到的取消也不能改变已经完成的记录。

## 超时需要两只时钟

单一的不活跃计时器不够。

使用两个限制：

1. **空闲超时：** 请求最多可以多久没有产生有用活动。
2. **最大超时：** 从请求开始起计算的绝对墙钟预算。

进度可以重置空闲时钟，但绝不能取消最大截止时间。

```text
start: 0 ms
progress: 400 ms
progress: 800 ms
progress: 1200 ms
idle timeout: 500 ms
maximum timeout: 2000 ms
```

在 1500 ms 时，请求仍然活跃，因为最近一次进度距现在只有 300 ms；在 2000 ms 时，即使 1999 ms 又到达了一次进度，最大截止时间仍会取消请求。

进度是可选的。服务器可以接受 progress token 而不发送任何更新。不要因为存在 token 就把超时变成无限。MCP 进度值必须递增。完成或取消后停止发送通知。对进度限速，避免快速 worker 淹没传输层。

## 请求取消不是 `tasks/cancel`

这几种机制服务于不同的生命周期。

| 机制 | 目标 | 信号 | 成功意味着什么 |
|-----------|--------|--------|--------------------|
| stdio 上的请求取消 | 一个正在执行的 RPC | `notifications/cancelled` | 客户端放弃请求；服务器应在可行时停止 |
| HTTP 上的请求取消 | 一个正在执行的响应流 | 关闭流 | 客户端放弃请求；服务器应在可行时停止 |
| `tasks/cancel` | 一个持久化 Task | 普通 MCP 请求 | 服务器确认了取消意图 |

成功的 `tasks/cancel` 结果不能证明 worker 已停止。worker 在检查点观察到标记之前，任务可能仍是 `working`；在检查点之前工作也可能已经完成。

HTTP 连接关闭时，不要删除持久化任务状态。创建 Task 的理由，正是它的生命周期能够超出一次请求和一次连接。

## 新的 JSON-RPC ID 不是幂等性

JSON-RPC id 用来关联请求和响应，不用于标识业务操作。

假设客户端用 id `41` 提交扣款，却丢失了响应，然后用 id `42` 重试。服务器看到的是两条不同的消息。没有应用层 key，它无法知道这两条消息其实对应同一个结账操作。

幂等键标识业务意图：

```json
{
  "name": "charge_account",
  "arguments": {
    "account": "acct-7",
    "cents": 1200,
    "idempotencyKey": "checkout-7"
  }
}
```

服务器保存：

- key；
- 操作参数的指纹；
- 已提交的结果。

相同 key 加相同参数会返回存储的结果；相同 key 加不同参数会被拒绝。这能防止 key 被意外复用来改变另一项业务操作。

### 账本边界必须原子且持久化

下面的顺序不安全：

```text
check key
run mutation
store result
```

两个 worker 都可能观察到 key 不存在，然后都执行变更。若副作用已经发生、但进程在写入存储前崩溃，重试时也会产生同样的歧义。

本课使用文件型 SQLite 账本。`BEGIN IMMEDIATE` 将 key 检查、模拟业务副作用、执行计数器和结果保存串行化到同一事务中。因此，使用同一 key 竞争的两个独立账本连接会观察到一个已提交结果和一次执行。关闭并重新打开账本后，该记录仍然存在。

每次返回值都从存储的 JSON 重建。调用者不会收到账本持有的可变对象，因此修改返回的字典不会污染后续重放结果。

模拟器的业务副作用是同一 SQLite 事务中的收据和执行计数器。现实中的支付、部署或外部 API 调用，不会仅仅因为写入本地表就变得原子。生产系统需要持久共享数据库事务、事务性 outbox，或由上游服务强制执行同一幂等键。进程锁不能保护多个副本，也不能跨重启生效。

### 重试矩阵

在实现重试前先完成分类。

| 类别 | 示例 | 重试规则 |
|------|---------|------------|
| 安全 | 没有副作用的确定性读取 | 理解失败边界后，可以用新的 JSON-RPC id 重试 |
| 有条件 | 带持久化幂等键的变更 | 使用相同 key 和完全相同的参数重试 |
| 不安全 | 没有业务去重的变更 | 不要自动重试；先完成对账 |

工具注解如 `readOnlyHint` 和 `idempotentHint` 仍是不受信任的提示。重试安全性由应用契约和服务器实现决定。

## 背压是正确性的一部分

SSE 生产者可能比客户端、代理或网络消费得更快。无界队列会把缓慢转化为内存耗尽。

使用有界队列，并明确哪些内容允许丢失。

进度是可替换的。同一 token 的较新进度会取代较早进度；最终 JSON-RPC 响应不可替换。

本课的缓冲区采用以下策略：

1. 合并同一 token 相邻的进度。
2. 达到容量时丢弃最早的进度。
3. 标记流需要从权威来源重新获取。
4. 保留最终响应。
5. 如果要保留最终响应就必须丢弃另一个最终响应，则拒绝进入这种状态。

这是带有显式恢复路径的有界丢失；静默丢失不是策略。

### 代理缓存

服务器可能正确地流式发送，而反向代理却把事件留在缓冲区中。

对于 SSE 响应，发送：

```http
Content-Type: text/event-stream
Cache-Control: no-cache
X-Accel-Buffering: no
```

2026 版 Streamable HTTP 规范建议使用 `X-Accel-Buffering: no`，让兼容的代理立即传递事件。

对于安静的长连接流，定期发送 SSE 注释：

```text
:
```

客户端会忽略注释行。中间层能看到流量，也就不那么容易关闭空闲连接。

Keepalive 不是进度。不要仅因为传输注释到达，就重置操作语义上的空闲超时。

## 重连意味着重新获取

现代 Streamable HTTP 不通过 `Last-Event-ID` 支持可恢复的 SSE。

`subscriptions/listen` 流断开后：

1. 用新的 JSON-RPC id 发起新的 listen 请求。
2. 恢复所需的订阅过滤器。
3. 通过权威方法重新获取受影响的工具、资源、提示或 Task。
4. 使用稳定标识符对应用状态去重。
5. 不要仅仅因为变更响应丢失，就重放不安全的变更。

示例恢复计划明确把 `sendLastEventId` 设为 false，并列出需要重新获取的资源。

### 防止重连风暴

如果 10,000 个客户端恰好在一秒后同时重连，正在恢复的服务器会再次失败。

使用带抖动和上限的指数退避。本课根据客户端 id 和尝试次数计算确定性抖动，使测试保持可复现：

```text
attempt 0: up to 250 ms
attempt 1: up to 500 ms
attempt 2: up to 1000 ms
...
cap: 8000 ms
```

生产系统可以使用密码学安全随机数或运行时随机数。真正的不变量是分散重试，而不是某个固定公式。

## 构建它

`code/main.py` 构建了五个小型可靠性组件。

### `RequestCoordinator`

- 以空闲和最大截止时间启动正在执行的请求；
- 发送单调递增的进度通知；
- 生成正确的 stdio 或 HTTP 取消信号；
- 忽略无效的取消通知；
- 明确取消与完成之间的终态竞态；
- 保留服务器发出的、仅用于 stdio 订阅的取消路径。

### `MutationLedger`

- 证明两个 JSON-RPC id 在没有业务 key 时会执行两次；
- 使用文件型 SQLite 事务保存 key 检查、模拟副作用、执行计数器和结果；
- 在独立账本连接之间，以同一幂等 key 去重匹配参数；
- 拒绝同一个 key 配不同参数的复用；
- 返回防御性副本，并在重新打开后保留已提交记录。

### `DurableTaskService`

- 确认收到取消请求；
- 在 worker 检查点之前让 task 保持 `working`；
- 展示为什么确认收到不等于最终状态。

### `BoundedSseBuffer`

- 在压力下合并或丢弃进度；
- 记录需要从权威来源重新获取；
- 从不丢弃最终响应。

### 恢复辅助函数

- 返回对代理安全的 SSE header 和 keepalive 注释；
- 创建重连与重新获取计划；
- 用确定性指数退避和抖动分散重试。

## 交互实验

在不增加 sleep 的情况下运行四种事件顺序。

1. 启动请求 `A`，取消它，然后调用 `complete()`。
2. 启动请求 `B`，完成它，然后交付取消事件。
3. 启动请求 `C`，在每个空闲截止时间前发送进度，然后越过最大截止时间。
4. 通过 Streamable HTTP 启动请求 `D`，并关闭它的响应流。

为每个场景记录：

- 请求的终态；
- 是否存在最终响应；
- 放在线上的取消信号；
- 客户端应该忽略哪个事件。

然后把 `D` 改为 stdio。操作本身相同，但取消信号必须改变。

## 实践实验

为 `MutationLedger` 增加 `reserve_inventory` 变更操作。

要求：

1. key 绑定 SKU、数量、租户和操作名称。
2. 相同 key 加相同参数的重试返回第一次预留结果。
3. 数量改变的重试失败，且不能产生另一次预留。
4. 已提交但响应丢失的执行可以通过 key 对账。
5. 结果不记录 secret 或支付数据。
6. 客户端未提供 key 时禁用自动重试。
7. 模拟订阅断开，并在决定下一步前重新获取库存记录。
8. 让两个账本连接在屏障处同时提交同一个 key，断言只提交一个预留。
9. 修改第一次返回的预留对象，重放 key 并证明存储结果没有改变。
10. 关闭并重新打开账本文件，然后通过 key 对账预留。

保持实验诚实：如果库存位于另一个服务中，说明该服务是否接受同一个幂等 key；如果不接受，说明事务性 outbox 如何连接本地提交与远程副作用。

## 验证它

当以下陈述都成立时，本课完成：

- stdio 取消发送 `notifications/cancelled`，且不会收到响应。
- Streamable HTTP 取消会关闭请求流，不发送取消 POST。
- 取消先发生时会抑制最终响应。
- 完成先发生时会保留响应，并忽略迟到取消。
- 进度可以重置空闲超时，但永远不能重置最大超时。
- 仅更换 JSON-RPC id 会让变更再次执行。
- 在两个连接的并发竞争下，一个幂等 key 只执行一次。
- 已提交记录在重新打开后仍存在，重放返回防御性副本。
- 修改返回结果不会改变存储结果。
- 有界缓冲区保持在容量以内并保留最终响应。
- 重连使用新请求，不发送 `Last-Event-ID`，并重新获取受影响状态。
- `tasks/cancel` 确认后，直到 worker 观察到取消前，Task 仍不是终态。

## 生产失败模式

| 失败 | 可观察症状 | 正确响应 |
|---------|--------------------|------------------|
| HTTP 客户端 POST 取消通知 | 服务器和客户端对请求生命周期的判断不一致 | 关闭请求的 SSE 响应流 |
| 服务器接受取消后仍响应 | 客户端收到不可用的迟到结果 | 取消获胜时停止工作并抑制后续消息 |
| 进度重置每个截止时间 | 卡住的工作永远不结束 | 保留独立的绝对最大超时 |
| 把新 RPC id 当作去重 | 扣款、部署或删除执行两次 | 增加持久化的应用幂等 key |
| key 检查与副作用分离 | 并发 worker 都观察到 key 不存在 | 原子提交 key 占用、效果记录和结果 |
| 跨副本使用内存账本 | 重启或另一个 worker 忘记之前提交 | 使用共享持久存储或上游幂等机制 |
| 直接返回可变存储结果 | 调用者修改结果后污染重放 | 序列化已提交结果并返回防御性副本 |
| 复用 key 但改变参数 | 一个 key 别名指向两个业务意图 | 保存并比较参数指纹 |
| 无界进度队列 | 慢消费者导致内存上升 | 在边界内合并并丢弃可替换进度 |
| 压力下丢弃最终响应 | 客户端无法知道请求结果 | 预留容量或驱逐进度，绝不丢最终响应 |
| 代理缓存 SSE | 进度成批到达或在超时后才到达 | 关闭缓存并配置兼容的代理超时 |
| 假设存在 `Last-Event-ID` | 客户端从服务器不支持的状态恢复 | 用新请求重连并重新获取 |
| 所有客户端立即重连 | 恢复过程再次造成故障 | 使用带上限的指数退避和抖动 |
| 把 Task 确认当成最终取消 | UI 显示停止但 worker 仍在运行 | 轮询 Task 直到终态 |

工具生态综合课应把可靠性当作可执行证据，而不是架构图中的一段说明。

要求以下交付物：

- 一条幂等 key 记录和参数不匹配夹具；
- 并发同 key 记录、重新打开检查和变更别名检查；
- 一份有界缓冲区过载结果；
- 反向代理 SSE header 与空闲策略；
- 一份写明权威重新获取方法的重连计划；
- 综合课使用 Tasks 时，一条持久化 Task 取消轨迹。

本地进程中的绿色请求只能证明快乐路径。只有当响应丢失、迟到取消、慢消费者和重连风暴都有确定性结果时，综合课才算生产就绪。

## 关键术语

| 术语 | 含义 |
|---------|------|
| 请求取消 | 放弃一个正在执行的 MCP 请求 |
| 取消竞态 | 终态完成事件与取消事件之间的竞争 |
| 空闲超时 | 距离上一次有用请求活动的限制 |
| 最大超时 | 从请求开始计算、不受进度影响的绝对限制 |
| 幂等键 | 去重一次业务意图的应用标识符 |
| 原子账本 | 将 key 占用、效果记录和结果作为一个单元持久提交的边界 |
| 背压 | 生产者快于消费者时施加的控制 |
| 进度合并 | 用较新的权威值替换较旧进度 |
| 重新获取 | 流出现间隙后再次读取当前状态 |
| 抖动 | 有意引入的时间变化，用于分散重试 |
