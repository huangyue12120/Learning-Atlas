# 流水线并行与气泡分析

> 张量并行将矩阵乘法拆分到不同 rank 上；流水线并行则将模型拆分到不同 rank 上，每个 rank 负责一个阶段。微批次沿流水线流动。开头和结尾的空闲时间就是气泡；如何把它降到最低，正是流水线并行的核心。

**类型：** 构建
**语言：** Python
**前置知识：** Phase 19 Track C 第 42–49 课
**用时：** 约 90 分钟

## 学习目标

- 将一个顺序模型拆分成 N 个阶段，并模拟跨 N 个 rank 的前向流水线。
- 使用 GPipe 调度（先只进行前向填充，再进行反向排空）让 M 个微批次通过流水线，并计算气泡占比。
- 将气泡情况与 Megatron-LM 和 PipeDream 使用的交错式 1F1B 调度进行比较。
- 论证阶段分配应优先保证各阶段计算量相等，而不是各阶段参数数量相等。

## 问题

一个使用 fp16、拥有 70B 参数的模型，光参数就需要 140 GB。没有任何消费级 GPU 能装下它。ZeRO-3 会跨 rank 分片参数，但每一步前向仍要求每个 rank 对完整层执行 `allgather`，每层都要付出 log(N) 跳的代价。流水线并行采取了另一条路径：把模型切成 N 个阶段，每个 rank 放置一个阶段。第 1 层在 rank 0 上完成前向后，将激活张量交给 rank 1；rank 1 运行第 2 层，再交给 rank 2；依此类推。反向传播则沿相反方向流动。由于每个 rank 只持有一个阶段，内存线性下降；但计算是串行的，这就产生了气泡问题。

气泡是流水线开始时的空闲时间（等待第一个微批次到达最后一个阶段）和结束时的空闲时间（等待最后一个微批次反向排空）。当有 M 个微批次、N 个阶段时，每个阶段的气泡占比为 (N-1)/(M+N-1)。M=8、N=4 时，占比为 27%；M=64、N=4 时，占比为 4.5%。每一步使用的微批次越多，气泡就越小；这意味着每个微批次的 batch size 要更小，也正是这一约束推动了微批次设计。

## 概念

```mermaid

  R0[rank 0：阶段 0 / 层 0] --> R1[rank 1：阶段 1 / 层 1]
  R1 --> R2[rank 2：阶段 2 / 层 2]
  R2 --> R3[rank 3：阶段 3 / 损失]
  R3 -.反向传播.-> R2
  R2 -.反向传播.-> R1
  R1 -.反向传播.-> R0
```

### GPipe 调度

先让全部 M 个微批次完成前向填充，再开始任何反向传播；随后按相反顺序进行反向排空。每个微批次的激活值都必须保留到对应的反向传播，因此内存会随 M 线性增长。前向需要 M+N-1 个周期，反向还需要另外 M+N-1 个周期。每个阶段的有效工作量是 2M 个周期，气泡是 2(N-1) 个周期。当每次前向和反向都耗时一个单位时，气泡占比为 (N-1)/(M+N-1)。让 M 远大于 N，就能隐藏气泡。

### 1F1B 调度

交错执行：一个微批次的前向到达最后阶段后，立即启动它的反向传播，让它沿流水线返回。该调度让每个阶段交替执行一次前向和一次反向。气泡仍为 N-1，但激活内存的上限由流水线深度决定，而不是微批次数量。生产流水线使用 1F1B（Megatron、PipeDream）。本课先实现更简单的 GPipe，把 1F1B 留作练习。

### 为什么各阶段计算量均衡很重要

如果阶段 0 需要 50 ms，而阶段 1 需要 100 ms，那么每个周期都会受阶段 1 限制。其他阶段每个周期都要空闲 50 ms，等待阶段 1 释放。用参数数量相等作为标准是错误的：Transformer 的计算量主要来自每层的注意力和 MLP，而嵌入层虽然参数很多，计算量却很小。阶段分配应当均衡每个阶段的 FLOPs，而不是均衡权重数量。

### 微批次与批次

一条流水线运行 M 个微批次，每个微批次大小为 B。有效 batch size 是 M*B。一个流水线 step 结束时的梯度，等价于对合计 M*B 个样本计算得到的梯度。气泡占比取决于 M，而优化器看到的是 M*B。调节 M，就是在气泡（M 较大时更小）与每个微批次的内存占用（对于 GPipe，M 较大时激活内存更高）之间做权衡。

## 构建

`code/main.py` 实现了：

- `PipelineStage`：一个小型 `nn.Module`，持有一个阶段的参数并提供 `forward(activation)`。

## 生产环境中的模式

三种模式可以把流水线并行加固到足以投入生产。

**激活检查点与流水线并行相辅相成。** GPipe 同时处理 M 个在途微批次时，激活内存是单个微批次的 M 倍。激活检查点会在反向传播时重新计算前向，以计算换内存；两者结合，才能让长序列上的流水线并行变得可行。

**阶段均衡要靠测量，而不是靠假设。** 生产团队会先在目标硬件上执行一次性能分析，测量每层的实际计算量（FLOPs 和墙钟时间），再依据测量结果进行切分。Megatron-LM 的 `--num-layers-per-stage` 标志接受一个列表，使每个阶段在单层成本不同时可以拥有不等的层数。

**send-recv 调度必须避免死锁。** 如果每个阶段都先发送再接收，流水线就会在线路上死锁。标准修复方式是交错发送和接收：偶数 rank 的阶段先 send 再 recv，奇数 rank 的阶段先 recv 再 send。本课显式调度各个 rank，让这种模式清晰可见。

## 使用

生产模式：

- **Megatron-LM。** 大规模流水线并行的参考实现。使用 1F1B，并支持张量并行 + 流水线并行 + 数据并行的组合。
- **DeepSpeed Pipeline。** 与 ZeRO 集成；ZeRO-1 + 流水线并行是超大规模开放模型常用的组合。
- **PyTorch Pipe。** PyTorch 原生的流水线包装器，构建在 `torch.distributed.pipeline.sync.Pipe` 之上。

## 练习

1. 实现 1F1B，并验证气泡占比与 GPipe 相同，但激活内存受到上限约束。
2. 在更深的模型上分析每个阶段的实际耗时，并依据测得的墙钟时间重新平衡阶段。
3. 在流水线微批次之间加入梯度累积，并检查所得梯度是否等于等效完整 batch 前向的梯度。
4. 将流水线并行与激活检查点结合起来，测量内存下降幅度与计算代价。
5. 将流水线并行与 DDP 组合（每个流水线 rank 都在一个数据并行组中复制），并推演二维调度。

## 关键术语

| 术语 | 常见说法 | 实际含义 |
|------|----------------|------------------------|
| Pipeline | “沿深度进行模型并行” | 每个 rank 负责一个阶段，激活值逐阶段流动 |
| Bubble | “流水线空闲时间” | 开头和结尾各有 (N-1) 步，此时部分阶段没有工作 |
| Microbatch | “batch 的切片” | 一个前向/反向单元；M 增大时气泡变小 |
| GPipe | “先填充再排空” | 先完成全部 M 次前向，再进行任何反向；激活内存较高 |
| 1F1B | “交错式调度” | 每个阶段交替进行一次前向和一次反向；激活内存有上限 |
